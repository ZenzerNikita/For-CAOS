# Артефакты

## Стадии компиляции программ

В прошлый раз мы запускали компиляцию программы на языке C с помощью простой командной строки, например:

```bash
gcc -Wall -Werror hello.c -o hello
```

Но если посмотреть на процесс компиляции поближе, то окажется, что компиляция программы состоит из нескольких
стадий. Теперь мы их рассмотрим подробнее.

### Препроцессирование

Как правило, файл с программой на C начинается с директив `#include`. По смыслу они аналогичны директивам `import`
других языков программирования. Но с точки зрения реализации директива `#include` &mdash; это просто текстовая подстановка
содержимого указанного файла вместо директивы. Например, в случае

```c
#include <stdio.h>
```

компилятор ищет в каталогах из специального списка файл с именем `stdio.h` и подставляет его содержимое вместо
этой строки. В Linux системах этот файл находится по пути `/usr/include/stdio.h`. Вы можете его открыть
в любом текстовом редакторе и убедиться, что это файл на языке C.
В подставляемом файле могут быть другие директивы `#include`, они тоже будут заменены на содержимое соответствующих
файлов, пока все директивы `#include` не будут обработаны.

Шаг подстановки всех файлов называется препроцессирование, а программа (часть компилятора C) называется препроцессор.
Результатом препроцессирования является один файл на языке C, который называется _единица трансляции_ (translation unit)
или _единица компиляции_ (compilation unit).

Кроме подстановки содержимого файлов препроцессор выполняет удаление комментариев из программы,
макроподстановки, то есть подстановку текста макроопределения в место использования макроса, и
условную компиляцию. Препроцессор языка C &mdash; это макропроцессор со своим языком, который на входе
получает текстовый файл программы на C и на выходе производит текстовый файл программы на C.
Команды (директивы) для препроцессора начинаются с символа `#`, который должен быть первым непробельным
символом в строке. Мы рассмотрим некоторые директивы препроцессора (`#define`, `#if`, `#else`, `#endif`)
в дальнейшем.

Существуют более мощные макропроцессоры специального или общего назначения, например LaTeX или m4, но и
препроцессор языка C позволяет многое, а в современных версиях C берет на себя функции, аналогичные generic
в Java или Golang или template в C++.

Ранее препроцессирование могло выполняться отдельной программой, запускаемой перед основной компиляцией
(традиционно эта программа называется `cpp`), но в современных компиляторах шаг препроцессирования
интегрирован в основной компилятор и отдельно не запускается. Это сделано и для ускорения работы,
и для улучшения возможностей отладки программы, чтобы в отладочной информации, которая генерируется
компилятором, сохранилась информация о макросах в исходной программе.

По соглашению, принятому в мире Unix, если результат препроцессирования сохраняется в файле,
файл имеет суффикс `.i` для программы на C, и `.ii` для программы на C++.

Вы можете посмотреть на результат работы препроцессора, если укажете в командной строке
компиляции опцию `-E`.

```bash
gcc -E hello.c
```

Эта команда выведет результат препроцессирования на стандартный поток вывода. Дальнейшие
шаги компиляции выполняться не будут.

```bash
gcc -E hello.c -o hello.i
```

Эта команда запишет результат препроцессирования в файл `hello.i`

### Трансляция

Единица трансляции, полученная в результате препроцессирования входного файла, подаётся
на вход собственно транслятору языка C. Он выполняет действия по анализу входной
программы: проверке её синтаксической структуры, проверке контекстных условий,
оптимизации программы и её переводу на систему команд целевого процессора.

Традиционно в POSIX-системах результат работы транслятора представляется не в форме
машинного кода с инструкциями в закодированной для процессора форме, а форме
программы на языке ассемблера.

Язык ассемблера &mdash; это текстовое представление программы в машинном коде. Вместо отдельных
битов, кодирующих инструкцию процессора и формат аргументов, в программе на языке
ассемблера используются текстовые обозначения. Вместо адресов размещения
операндов используются текстовые идентификаторы &mdash; метки.

Некоторые современные компиляторы, например clang или msvc не генерируют в качестве промежуточного
шага программу на языке ассемблера, а сразу выдают объектный файл, но и они
могу выдавать программу на языке ассемблера по запросу пользователя.

Вы можете посмотреть на программу на языке ассемблера для исходного кода на Си,
если укажете в командной строке опцию `-S`.

```bash
gcc -S -O2 hello.c
```

Эта команда возьмёт в качестве компилируемого файла на C файл `hello.c` и
запишет файл на языке ассемблера в файл `hello.s`.

Хотя система команд (так называемая Instruction Set Architecture &mdash; ISA)
специфична для каждого типа процессоров (Intel x86, ARM, RiscV),
все они достаточно похожи друг на друга, чтобы, зная одну из систем команд,
в принципе понимать другие. Краткое введение в ISA для одного из
типов современных процессоров будет далее в нашем курсе.

### Ассемблирование

На шаге ассемблирования программа на языке ассемблера, полученная на предыдущем
шаге преобразуется в объектную программу. Например, команда

```bash
gcc -O2 hello.c -c
```

сгенерирует из входного файла `hello.c` объектный файл `hello.o`.

Можно считать, что компиляция завершается с получением объектного файла. Следующий
шаг &mdash; компоновка &mdash; в большинстве случаев выполняется отдельно от компиляции.

В POSIX-совместимых операционных системах программа-ассемблер называется `as`.
Она при необходимости может быть запущена и самостоятельно.
Программа-ассемблер может не входить в состав программного пакета компиляции
и поставляться независимо. Например, в Linux компилятор GNU C обычно находится
в составе пакета `gcc`, а ассемблер &mdash; в составе пакета `bintutils`.

### Компоновка

Компоновка &mdash; финальная стадия создания исполняемой программы.
Программа-компоновщик (иногда используют слово-кальку «линкер» от linker)
объединяет поданные ей на вход объектные файлы, добавляет к ним
необходимые объектные файлы из статических библиотек,
проверяет наличие необходимых имён в динамических библиотеках.
При компоновке каждого объектного файл для каждого
импортируемого в него имени находится объектный файл, который
экспортирует это имя, и таким образом определения функций
и глобальных переменных связываются с их использованиями
во всей программе.
Компоновщик также выполняет некоторые оптимизации программы
(так называемые link time optimization &mdash; LTO).
В итоге получается исполняемый файл. Работа компоновщика будет описана более
подробно далее.

Важно заметить, что при связывании имен при компоновке не учитывается,
какой тип имело имя в исходном коде на языке программирования
высокого уровня. Важно только имя, то есть строка символов.
Отсюда возникает идея «декорирования имен» (name mangling), которую мы подробнее обсудим ниже.

В POSIX-совместимых системах программа-компоновщик называется `ld`.
На Linux компоновщик входит в состав пакета `binutils`, хотя, например, clang
поставляется со своим компоновщиком.

### Драйвер компиляции

Поскольку компиляция программы на C может включать в себя несколько шагов
и начинаться и оканчиваться на любом из них, компилятор GNU C предоставляет
программу-драйвер компиляции `gcc`. Для компиляции C++ программа-драйвер
называется `g++`, Фортрана &mdash; `gfortran` и т. д.
Аналогично компилятор LLVM предоставляет драйвер компиляции `clang` или `clang++`.

Кроме того, в POSIX-совместимой операционной системе обычно есть команда `cc`,
вызывающая некий компилятор C «по умолчанию». В Linux &mdash; это обычно `gcc`,
на MacOS или BSD &mdash; это обычно `clang`. Иногда, например на Ubuntu, после имени компилятора указывается
суффикс его версии, например `gcc-14` или `clang-17`.
Обратите внимание, что на MacOS «из коробки» команда `gcc` является синонимом `clang` от компании Apple,
который немного отличается от LLVM clang. Чтобы установить «настоящий» `gcc` потребуется
установить homebrew.

Чтобы узнать версию компилятора, установленную в системе, можно выполнить команду `gcc -v`.
Будет выведено примерно следующее:

```
Using built-in specs.
COLLECT_GCC=/opt/homebrew/opt/gcc/bin/gcc-15
COLLECT_LTO_WRAPPER=/opt/homebrew/Cellar/gcc/15.1.0/bin/../libexec/gcc/aarch64-apple-darwin24/15/lto-wrapper
Target: aarch64-apple-darwin24
Configured with: ...
Thread model: posix
Supported LTO compression algorithms: zlib zstd
gcc version 15.1.0 (Homebrew GCC 15.1.0)
```

То есть это &mdash; компилятор gcc версии 15.1 для MacOS на Apple Silicon.

Если добавить флаг `-v` к обычной командной строке компилятора, например `gcc -v hello.c -o hello`,
будет выведено много информации о том, какие компоненты компилятора запускались и какие аргументы
им передавались.

Прочие полезные опции gcc перечислены в таблице.

| Опция | Описание |
| - | - |
| `-I PATH` | (Препроцессор.) Добавляет каталог `PATH` в начало списка каталогов, которые просматриваются препроцессором при поиске файлов, подключаемых директивой `#include`. В командной строке может быть указано несколько опций `-I`, тогда каталоги просматриваются в порядке, в котором они указаны в командной строке. |
| `-D NAME` | (Препроцессор.) Определяет макрос с именем `NAME`, который получает значение 1. |
| `-D NAME=VALUE` | (Препроцессор.) Определяет макрос с именем `NAME`, который получает заданное значение `VALUE`. |
| `-Wall` | (Транслятор.) Включает выдачу разных типов предупреждающих сообщений (warning), которые по умолчанию не выдаются. Опция должна использоваться при компиляции программ, все предупреждающие сообщения компилятора должны быть внимательно проанализированы, поскольку сообщения могут указывать на ошибки в программе. |
| `-Werror` | (Транслятор.) Предупреждения расцениваются как ошибки компиляции. |
| `-std=STD` | (Все стадии.) Активирует поддержку стандарта `STD`. Поддерживаются стандарты `gnu17`, `gnu23`, `gnu99` для языка Си, `gnu++20`, `gnu++23` для языка Си++ и другие. |
| `-g` | (Транслятор.) Включает генерацию отладочной информации в исполняемую программу. Наличие отладочной информации позволяет отлаживать программу в терминах исходного языка, а не машинного кода. |
| `-O2` | (Транслятор.) Включает большинство оптимизаций программы, которые одновременно уменьшают размер программы и увеличивают скорость её выполнения. |
| `-fsanitize=OPT` | (Все стадии.) Включает режим динамического контроля (sanitizers) разных типичных ошибок переполнений, выходов за границы массива и ошибок параллельного программирования. |
| `-L PATH` | (Компоновщик.) Добавляет путь `PATH` в начало списка каталогов, которые просматриваются редактором связей при поиске библиотек, указанных с помощью опции `-l`. Если в командной строке указано несколько опций `-L`, они добавляются в том же порядке, в котором указаны в командной строке. |
| `-lNAME` | (Компоновщик.) Добавляет библиотеку `NAME` к списку библиотек, которые участвуют в компоновке программы (обратите внимание на отсутствие пробела между опцией и именем библиотеки). В системах Unix редактор связей просматривает библиотеки один раз, поэтому неправильный порядок задания библиотек может привести к тому, что некоторые имена останутся неопределёнными, и компиляция завершится с ошибкой. Файл, хранящий библиотеку с именем `NAME`, называется `libNAME.a`, если библиотека статическая, и `libNAME.so`, если библиотека динамическая. |
| `-static` | (Компоновщик.) Указывает, что при компоновке не должны использоваться динамические библиотеки. Реализации всех используемых в программе функций будут добавлены непосредственно в исполняемый файл. Подробнее смотри ниже. |
| `-shared` | (Компоновщик.) Указывает, что результатом сборки программы должен быть разделяемый объектный файл (so-файл), то есть динамически подгружаемая библиотека. |


## Стандартные суффиксы имён файлов

Традиционно файлы с определённым содержимым называются определённым образом. Например,
файл `image.jpg` &mdash; это, скорее всего, файл с изображением в формате JPEG. К исполнению
этих соглашений никто не принуждает, и компьютерные вирусы в файле с суффиксом
`.jpg` могут хранить программный код, но, как вы понимаете, это не нормальная практика.

В контексте работы компиляторов чаще всего встречаются следующие суффиксы файлов.

| Суффикс | Описание |
| - | - |
| `.c` | Исходный код программы на C |
| `.h` | Заголовочный файл на языке C или C++ |
| `.cpp`, `.cc`, `.cxx`, `.C` | Исходный код программы на C++ |
| `.hpp` | Заголовочный файл программы на C++ |
| `.i` | Программа на C после препроцессирования |
| `.ii` | Программа на Си++ после препроцессирования |
| `.s` | Программа на языке ассемблера |
| `.S` | Программа на языке ассемблера, предназначенная для препроцессирования |
| `.o` | Объектный файл |
| `.a` | Статическая библиотека |
| `.so` | Разделяемый объектный файл (динамическая библиотека) в формате ELF |
| `.dylib` | Динамическая библиотека в формате Mach-O (на MacOS) |

Драйвер компиляции `gcc` умеет обрабатывать разные типы файлов, переданные ему в командной строке.
По умолчанию, если суффикс имени файла не относится к списку обрабатываемых
суффиксов, имя файла передаётся компоновщику на стадию компоновки.

Обрабатываются файлы со следующими суффиксами:

| Суффикс | Обработка |
| - | - |
| `.h`, `.hpp` | Выдаётся сообщение об ошибке, заголовочные файлы не предназначены для компиляции |
| `.c` | Файл на языке C, который требует препроцессирования, компиляции C и т. д. |
| `.cpp`, `.cc`, `.cxx`, `.C` | Файл на языке C++, требующий препроцессирования, компиляции C++ и т. д. |
| `.i` | Файл на языке C после препроцессирования, требует компиляции |
| `.ii` | Файл на языке C++ после препроцессирования, требует компиляции |
| `.s` | Файл на языке ассемблера, не требующий препроцессирования |
| `.S` | Файл на языке ассемблера, требующий препроцессирование |

Когда в командной строке `gcc` указывается несколько файлов с разными суффиксами, вид
обработки выбирается для каждого файла в зависимости от его суффикса индивидуально.
Например,

```bash
gcc a.c b.s c.S d.cpp -o res
```

Для файла `a.c` будет выполняться препроцессирование, трансляция из C, ассемблирование;
для файла `b.s` будет выполняться только ассемблирование;
для файла `c.S` будет выполняться препроцессирование и ассемблирование;
для файла `d.cpp` будет выполняться препроцессирование, трансляция из C++, ассемблирование.
Полученные четыре объектных файла `a.o`, `b.o`, `c.o`, `d.o` будут объединены в
одну исполняемую программу компоновщиком.

## Объектные и исполняемые файлы

Как мы уже знаем, для хранения исполняемых файлов в Linux используется формат ELF,
на MacOS &mdash; формат Mach-O, на Windows &mdash; формат PE. Далее мы будем
обсуждать формат ELF, но все сказанное будет справедливо и для других форматов
хранения исполняемых файлов.

Формат ELF используется не только для исполняемых файлов, но и для объектных файлов
и разделяемых объектных (Shared Object &mdash; SO) файлов. Объектный файл является результатом
обработки одной единицы трансляции компилятором C.

Упрощенно, ELF-файл имеет следующую структуру. Он состоит из секций, в одну секцию
группируются логически близкие сущности программы. Например, традиционно
в секции `.text` в ELF-файле находятся тела функций, то есть машинные инструкции,
сгенерированные компилятором для функций на языке программирования высокого уровня.
В C++ компилятор может помещать тело каждой функции в отдельную секцию.
Секции группируются в сегменты, то есть блоки, которые ведут себя одинаково
с точки зрения размещения в памяти программы при выполнении. ELF-файл содержит таблицу
символов, то есть идентификаторов переменных и функций, определённых в
данной единице трансляции или используемых в ней.

Объектный файл, то есть то, что выдаёт компилятор для каждой единицы трансляции,
отличается от финального исполняемого файла в следующем:
* секции объектного файла не размещены в памяти, то есть для них не указаны адреса в оперативной памяти, по которым они должны размещаться при выполнении программы;
* так как секции не размещены в памяти, машинный код функций содержит «предварительные» адреса, которые должны быть исправлены (релоцированы) при размещении секции в памяти;
* у объектного файла нет точки входа, с которой должно начаться выполнение программы.

У исполняемого файла в формате ELF секции размещены по адресам, хотя при выполнении
программы эти адреса и могут измениться; никаких правок в машинном коде функции для исполнения
не требуется; и есть точка входа. Разделяемый объектный файл, или, говоря более традиционно,
динамическая библиотека, является разновидностью исполняемого файла.

Рассмотрим пример. Пусть дана программа в файле `sum.c`.

```c
#include <stdio.h>

int x = 1, y;
int compute()
{
    return x + y;
}

int main()
{
    [[maybe_unused]] int r = scanf("%d%d", &x, &y);
    printf("%d\n", compute());
}
```

Конструкция `[[maybe_unused]] int r` объявляет переменную `r` типа `int`,
значение которой разрешено не использовать. Это &mdash; способ
подавить предупреждение компилятора о необходимости проверки возвращаемого
значения функции `scanf`. Не делайте так в своих программах, всегда
проверяйте возвращаемое значение `scanf`.

### Что находится в объектном файле

В этой программе объявлены две глобальных переменных `x` и `y` и функции `compute` и `main`.
Скомпилируем программу в объектный файл.

```bash
gcc -O2 sum.c -c
```

В результате был создан файл `sum.o`. Выведем общую информацию о файле:

```bash
objdump -f sum.o
```

Получим примерно следующее:

```
sum.o:     file format elf64-x86-64
architecture: i386:x86-64, flags 0x00000011:
HAS_RELOC, HAS_SYMS
start address 0x0000000000000000
```

В объектном файле присутствуют релокации (`HAS_RELOC`) и таблица символов (`HAS_SYMS`).

Выведем таблицу секций объектного файла.

```bash
objdump -h sum.o
```

Получим примерно следующее:

```

Sections:
Idx Name          Size      VMA               LMA               File off  Algn
  0 .text         00000013  0000000000000000  0000000000000000  00000040  2**4
                  CONTENTS, ALLOC, LOAD, RELOC, READONLY, CODE
  1 .data         00000004  0000000000000000  0000000000000000  00000054  2**2
                  CONTENTS, ALLOC, LOAD, DATA
  2 .bss          00000004  0000000000000000  0000000000000000  00000058  2**2
                  ALLOC
  3 .rodata.str1.1 00000009  0000000000000000  0000000000000000  00000058  2**0
                  CONTENTS, ALLOC, LOAD, READONLY, DATA
  4 .text.startup 0000003e  0000000000000000  0000000000000000  00000070  2**4
                  CONTENTS, ALLOC, LOAD, RELOC, READONLY, CODE
  5 .comment      0000002f  0000000000000000  0000000000000000  000000ae  2**0
                  CONTENTS, READONLY
  6 .note.GNU-stack 00000000  0000000000000000  0000000000000000  000000dd  2**0
                  CONTENTS, READONLY
  7 .note.gnu.property 00000030  0000000000000000  0000000000000000  000000e0  2**3
                  CONTENTS, ALLOC, LOAD, READONLY, DATA
  8 .eh_frame     00000048  0000000000000000  0000000000000000  00000110  2**3
                  CONTENTS, ALLOC, LOAD, RELOC, READONLY, DATA
```

Секциям не назначены адреса в памяти (VMA и LMA равны 0).
Секция `.text` хранит скомпилированный машинный код всех функций за исключением
функции `main`, которая помещена в секцию `.text.startup`.
Секция `.data` хранит явно инициализированные глобальные переменные,
а секция `.bss` хранит неявно инициализированные (то есть заполняемые значением 0)
или инициализированные нулём
глобальные переменные. У секции `.bss` отсутствует свойство `CONTENTS`, то есть
её содержимое не хранится в объектном файле. Для нее достаточно знать размер секции,
то есть общий размер глобальных переменных, неявно инициализированных значением 0.
У секции `.comment` отсутствуют свойства `ALLOC` и `LOAD`, то есть эта секция
находится только в объектном файле, под содержимое секции не выделяется оперативная память
и оно не грузится из объектного файла в память.

Секция `.rodata.str1.1` содержит строки, использованные в программе на C.
Мы можем посмотреть содержимое секции `.rodata.str1.1` с помощью команды

```bash
objdump -j .rodata.str1.1 -s sum.o
```

и увидим следующее:

```
sum.o:     file format elf64-x86-64

Contents of section .rodata.str1.1:
 0000 25642564 0025640a 00                 %d%d.%d..
```

Видим наши форматные строки с завершающим нулевым байтом.

Теперь посмотрим таблицу символов объектного файла.

```bash
objdump -t sum.o
```

Таблица символов нашего объектного файла должна иметь примерно такой вид:

```
sum.o:     file format elf64-x86-64

SYMBOL TABLE:
0000000000000000 l    df *ABS*  0000000000000000 sum.c
0000000000000000 l    d  .text  0000000000000000 .text
0000000000000000 l    d  .text.startup  0000000000000000 .text.startup
0000000000000000 l       .rodata.str1.1 0000000000000000 .LC0
0000000000000005 l       .rodata.str1.1 0000000000000000 .LC1
0000000000000000 g     F .text  0000000000000013 compute
0000000000000000         *UND*  0000000000000000 _GLOBAL_OFFSET_TABLE_
0000000000000000 g     O .bss   0000000000000004 y
0000000000000000 g     O .data  0000000000000004 x
0000000000000000 g     F .text.startup  000000000000003e main
0000000000000000         *UND*  0000000000000000 __isoc99_scanf
0000000000000000         *UND*  0000000000000000 printf
```

Среди глобальных символов (отмеченных `g` во втором столбце) есть три неопределённых
(`_GLOBAL_OFFSET_TABLE_`, `__isoc99_scanf` и `printf`). `_GLOBAL_OFFSET_TABLE` &mdash;
это специальная таблица, используемая для динамического связывания. Она автоматически
создаётся при компоновке программы, и о ней мы поговорим в своё время. Функция `__isoc99_scanf`
вызывается вместо `scanf`, если программа компилируется с включенной поддержкой
современных стандартов C.

Первый столбец &mdash; это адрес в памяти, и мы видим, что он не назначен ни одному
символу. Четвертый столбец &mdash; это имя секции, в которой он размещается,
пятый &mdash; его размер, а шестой &mdash; имя. Так, функция (потому что в
третьем столбце `F`) `compute` располагается в секции `.text` и имеет размер `0x13` байт.
Переменная `y` размещена в секции `.bss` потому что инициализируется нулём,
а переменная `x` размещена в секции `.data`.

Можем посмотреть таблицу релокаций:

```bash
objdump -r sum.o
```

У нее будет следующее начало:

```
sum.o:     file format elf64-x86-64

RELOCATION RECORDS FOR [.text]:
OFFSET           TYPE              VALUE
0000000000000002 R_X86_64_PC32     y-0x0000000000000004
0000000000000008 R_X86_64_PC32     x-0x0000000000000004
```

То есть в секции `.text` есть две релокации, первая находится
по смещению `0x2` от начала секции, и эти четыре байта (потому что `_PC32`) должны
после релокации хранить смещение от текущей точки программы до переменной `y`,
а вторые &mdash; до переменной `x`.

Мы можем распечатать инструкции процессора в файле, размещённые в секции `.text`:

```bash
objdump -j .text -D sum.o
```

Получим:

```
sum.o:     file format elf64-x86-64


Disassembly of section .text:

0000000000000000 <compute>:
   0:   8b 05 00 00 00 00       mov    0x0(%rip),%eax        # 6 <compute+0x6>
   6:   03 05 00 00 00 00       add    0x0(%rip),%eax        # c <compute+0xc>
   c:   c3                      ret
```

О языке ассемблера мы будем более подробно говорить в соответствующей части курса.

Итак, объектный файл &mdash; это «полуфабрикат», предназначенный для
последующей компоновки в исполняемую программу. Можно сравнить его
с кубиком Лего, который, зацепляясь с другими кубиками, формирует конструкцию.

### Что находится в исполняемом файле

Существуют четыре разновидности исполнямых файлов:
* динамически скомпонованный неперемещаемый исполнямый файл;
* динамически скомпонованный перемещаемый исполняемый файл;
* статически скомпонованный файл;
* разделяемый объектный файл (shared object), то есть динамическая библиотека.

Динамически скомпонованные файлы требуют для своей работы динамические библиотеки,
которые должны быть загружены в память программы. При запуске программы на выполнение
вместе с самой программой в память загружается _динамический загрузчик_
(в терминах ELF он называется _интерпретатор_), затем динамический загрузчик подгружает
в память динамические библиотеки, перечисленные в исполняемом файле и уже загруженных
динамических библиотеках. Затем динамический загрузчик обрабатывает часть
экспортов и импортов в библиотеках, связывая их друг с другом.
Как правило, вызовы функций, находящихся в динамических библиотеках, связываются
при первом вызове (так называемое «ленивое связывание» &mdash; lazy binding).
Подробнее о механизмах, с помощью которых выполняется связывание
исполняемого файла и динамических библиотек при загрузке и работе программы,
мы поговорим в свое время.

Чтобы получить список динамических библиотек, необходимых для программы,
используется команда `ldd`, например

```bash
ldd sum
```

Для простой программы вывод будет примерно таким:

```
        linux-vdso.so.1 (0x00007f7fceffe000)
        libc.so.6 => /lib64/libc.so.6 (0x00007f7fcedf2000)
        /lib64/ld-linux-x86-64.so.2 (0x00007f7fcf000000)
```

Здесь `ld-linux-x86-64.so.2` &mdash; это динамический загрузчик,
`libc.so.6` &mdash; стандартная библиотека C,
`linux-vdso.so.1` &mdash; «псевдобиблиотека» быстрых системных вызовов.

Большая программа может требовать для выполнения десятки динамических библиотек.

#### Неперемещаемые файлы

Динамически скомпонованный неперемещаемый исполняемый файл расчитан на загрузку в память
с определенного фиксированного в программе адреса. Этот адрес, как правило,
фиксирован для каждой архитектуры, но разные программы, загружаемые в память,
не мешают друг другу, так как для каждой программы создается свое виртуальное адресное
пространство. Загрузка в память по фиксированному адресу для некоторых процессорных
архитектур проще, чем перемещаемая загрузка, и программа, расположенная по фиксированному
адресу, может оказаться чуть быстрее. Загрузка по фиксированному адресу &mdash; традиционный
способ выполнения исполняемых файлов на Linux.

Например, в Fedora Linux неперемещаемые исполняемые файлы создаются по умолчанию.

Скомпилируем нашу программу в исполняемый файл:

```bash
gcc -O2 sum.c -Wall -o sum
```

У автора получился исполняемый файл размером 16760 байт.

Выведем общую информацию о файле.

```bash
objdump -f sum
```

Получим примерно следующий вывод.

```
sum:     file format elf64-x86-64
architecture: i386:x86-64, flags 0x00000112:
EXEC_P, HAS_SYMS, D_PAGED
start address 0x0000000000401090
```

Флаг `EXEC_P` означает, что файл подготовлен к исполнению, флаг `D_PAGED` означает,
что файл оптимизирован для страничной подкачки по требованию (demand paging),
то есть сегменты исполняемого файла с разными требованиями к загрузке
разнесены по разным страницам виртуальной памяти. О виртуальной памяти
мы будем много говорить в соотвествующем разделе курса.
У файла есть адрес точки входа `0x401090`, то есть на этот адрес в памяти будет
передано выполнение после загрузки файла в память.

Если мы выведем таблицу секций, то увидим, что секций в исполняемом файле стало намного больше,
чем в объектном файле, и они получили адреса.

```

  2 .note.gnu.build-id 00000024  0000000000400378  0000000000400378  00000378  2**2

  3 .note.ABI-tag 00000020  000000000040039c  000000000040039c  0000039c  2**2

  4 .gnu.hash     0000001c  00000000004003c0  00000000004003c0  000003c0  2**3
```

Если мы распечатаем содержимое секции `.interp`, то получим примерно такое:

```

```

То есть секция `.interp` содержит строку в формате C (с нулевым байтом на конце),
задающую путь к динамическому загрузчику.

В исполняемой программе таблица символов не нужна для выполнения
программы. Мы можем удалить таблицу символов из
исполняемого файла с помощью команды `strip -s sum`. Для связывания программы
с динамическими библиотеками используется динамическая таблица символов,
которую можно вывести с помощью команды

```bash
objdump -T sum
```

она будет примерно такой:

```
sum:     file format elf64-x86-64

DYNAMIC SYMBOL TABLE:
0000000000000000      DF *UND*  0000000000000000 (GLIBC_2.34) __libc_start_main
0000000000000000      DF *UND*  0000000000000000 (GLIBC_2.2.5) printf
0000000000000000  w   D  *UND*  0000000000000000  Base        __gmon_start__
0000000000000000      DF *UND*  0000000000000000 (GLIBC_2.7)  __isoc99_scanf
```

Четыре идентификатора отмечены как `*UND*`, то есть они должны быть
найдены при старте программы в подгружаемых динамических библиотеках.
В динамической таблице символов по умолчанию отсутствуют глобальные переменные и
функции самой программы. Чтобы они там появились при компиляции программы
нужно указать опцию `-rdynamic`:

```bash
 gcc -O2 sum.c -rdynamic -o sum
 ```

Получим динамическую таблицу символов, содержащую следующие строки:

```
sum:     file format elf64-x86-64

DYNAMIC SYMBOL TABLE:
0000000000000000      DF *UND*  0000000000000000 (GLIBC_2.34) __libc_start_main
0000000000000000      DF *UND*  0000000000000000 (GLIBC_2.2.5) printf
0000000000000000  w   D  *UND*  0000000000000000  Base        __gmon_start__
0000000000000000      DF *UND*  0000000000000000 (GLIBC_2.7)  __isoc99_scanf
0000000000404014 g    DO .data  0000000000000004  Base        x
000000000040401c g    DO .bss   0000000000000004  Base        y
0000000000401050 g    DF .text  0000000000000039  Base        main
0000000000401180 g    DF .text  000000000000000d  Base        compute
```

Мы видим, что переменная `x` разместилась в секции `.data` по адресу `0x404014`,
переменная `y` разместилась в секции `.bss` по адресу `0x40401c`.
Функция `compute` имеет адрес `0x401180`. Адрес, с которого программа
размещается в памяти, для архитектуры `x86-64` по умолчанию равен `0x400000`.
Его можно поменять на другой, например на `0x100000`, при компиляции программы
передав соответствующую опцию компоновщику.

```bash
gcc -O2 sum.c -Wall -o sum -Wl,-Ttext-segment=100000
```

#### Перемещаемые файлы

В некоторых вариантах Linux по умолчанию используются динамически скомпонованные перемещаемые
исполняемые файлы (потому что некоторые считают, что так «безопаснее»). Такие файлы
каждый раз загружаются на выполнение по новому случайному адресу, поэтому должны содержать
необходимые данные, позволяющие перемещать их в памяти. Динамически скомпонованные
перемещаемые исполняемые файлы по сути ничем не отличаются от разделяемых объектных файлов,
только наличием прописанного динамического загрузчика.

Динамически скомпонованный перемещаемый исполняемый файл можно получить командой

```bash
gcc -O2 sum.c -Wall -o sum -fPIE -pie
```

Опция `-fPIE` инструктирует транслятор из C в язык ассемблера генерировать
код для позиционно-независимых исполняемых файлов (position independent executable &mdash; PIE),
они же перемещаемые файлы, а опция `-pie` предназначена для компоновщика,
чтобы на выходе получился перемещаемый исполняемый файл.

Заголовок файла становится таким:

```
sum:     file format elf64-x86-64
architecture: i386:x86-64, flags 0x00000150:
HAS_SYMS, DYNAMIC, D_PAGED
start address 0x00000000000010b0
```

то есть теперь вместо флага `EXEC_P` появился флаг `DYNAMIC`,
указывающий, что адрес размещения программы в памяти должен быть
определен при загрузке программы в память.

В таблице секций адреса прописаны в предположении, что программа начинается
с нулевого адреса. Соответственно изменяются адреса в таблице символов.

```
sum:     file format elf64-x86-64

Sections:
Idx Name          Size      VMA               LMA               File off  Algn
  0 .interp       0000001c  0000000000000318  0000000000000318  00000318  2**0
                  CONTENTS, ALLOC, LOAD, READONLY, DATA
```

#### Разделяемый объектный файл

Разделяемый объектный файл (so-файл) отличается от перемещаемого исполняемого файла тем,
что предназначен для загрузки в качестве динамической библиотеки в 
память других программ. Поэтому у него нет точки входа.
Даже если текст программы содержит функцию `main`.

Скомпилировать so-файл можно командой

```bash
gcc -O2 sum.c -Wall -o sum -fPIC -shared
```

Здесь опция `-fPIC` включает режим генерации позиционно-независимого кода
на фазе трансляции из C в ассемблер, а опция `-shared` указывает
компоновщику, что на выходе должен быть создан разделяемый объектный файл.

Заголовок so-файла такой:

```
sum:     file format elf64-x86-64
architecture: i386:x86-64, flags 0x00000150:
HAS_SYMS, DYNAMIC, D_PAGED
start address 0x0000000000000000
```

то есть он совпадает с заголовком перемещаемого исполняемого файла, за исключеним
того, что у so-файла точка входа отсутствует.

#### Статически скомпонованная программа

Исторически первой схемой компоновки программы является статическая компоновка.
Статическая компоновка дает исполняемый файл, который не требует для выполнения динамических
библиотек и настроен на загрузку с фиксированного адреса. При статической компоновке
исполняемый файл может не содержать таблицу символов, на работоспособность это не влияет.

Получить статически скомпонованный исполнямый файл можно с помощью команды

```bash
gcc -O2 sum.c -Wall -o sum -static
```

Размер файла `sum` на системе автора равен 931896 байт. Исполняемый файл
стал намного больше из-за того, что машинный код всех необходимых для работы
программы библиотечных функций (`scanf`, `printf`) был добавлен
непосредственно в исполняемый файл. При таком большом начальном размере
в дальнейшем размер исполняемого файла будет расти не так быстро.
Поскольку таблица символов теперь не нужна для динамической компоновки программы,
её можно полностью удалить с помощью команды

```bash
strip -s sum
```

исполняемый файл станет немного меньше.
Заголовок ELF-файла стал таким:

```
sum:     file format elf64-x86-64
architecture: i386:x86-64, flags 0x00000102:
EXEC_P, D_PAGED
start address 0x00000000004016e0
```

И таблица символов стала пустой.

```
sum:     file format elf64-x86-64

SYMBOL TABLE:
no symbols
```

#### Сравнение статической и динамической компоновки

Динамическая компоновка имеет следующие преимущества перед статической:
* код динамической библиотеки находится в памяти в одном экземпляре и совместно используется всеми процессами, работающими в системе. Например, стандартная библиотека C, которая обычно на Linux называется glibc, в памяти занимает около 4MiB. Если в системе одновременно запущено 100 процессов, использующих стандартную библиотеку C, в итоге экономится примерно 400MiB оперативной памяти.
* исполняемые файлы получаются существенно меньшего размера, так как разделяемая библиотека не содержится в исполняемом файле.
* можно обновить динамическую библиотеку, исполняемые файлы будут использовать новую версию библиотеки.

Но у динамической компоновки есть недостатки. Исполняемая программа становится зависима от динамических библиотек, установленных на данной системе.
Возможно, и даже вероятнее всего, программа, скомпилированная для Fedora Linux, будет работать на Ubuntu Linux,
но на каком-нибудь Alpine Linux могут проявиться несовместимости.
Программа не запустится, если она была скомпилирована с одной версией библиотеки,
а в системе установлена более старая версия.

Поэтому, чтобы программа в бинарном виде была переносима на максимальное количество
разных версий Linux, её нужно компоновать статически. Кроме того, использование
контейнеризации с помощью docker или аналогичных средств нивелирует экономию памяти,
так как динамическая библиотека в контейнере не может использоваться в хост-системе.
Поэтому, например, компилятор языка Go генерирует статически скомпонованные
исполняемые файлы, да и в принципе язык Go не поддерживает динамическую компоновку.

### Что находится в архивном файле (.a-файле)

Для статической компоновки программы требуется статическая версия стандартной библиотеки
C. Этот файл называется `libc.a` и находится в каталоге `/usr/lib64`. Путь
к каталогу может варьироваться на разных версиях Linux. Файлы с суффиксом `.a`
называются архивными, или библиотечными, файлами. В Windows им соответствуют
библиотечные файлы с суффиксом `.lib`.

Архивный файл (статическая библиотека) &mdash; это архив (как zip, jar, tar)
объектных файлов. Он дополнительно снабжён общей таблицей символов,
в которой для каждого экспортируемого символа указано,
в каком объектном файле в составе библиотеки он определяется.
Задача компоновщика заключается в том, что, если компоновщику дан
идентификатор, который нужно привязать к определению,
компоновщик по общей таблице символов определит, в каком объектном
файле в составе библиотеки определяется нужный идентификатор,
и добавит этот объектный файл в состав выходного исполняемого файла целиком.

Чтобы посмотреть заголовок библиотечного файла можно воспользоваться командой

```bash
objdump -f /usr/lib64/libc.a
```

Команда выведет заголовок каждого объектного файла, находящегося в библиотеке.

```
In archive /usr/lib64/libc.a:

init-first.o:     file format elf64-x86-64
architecture: i386:x86-64, flags 0x00000011:
HAS_RELOC, HAS_SYMS
start address 0x0000000000000000


libc-start.o:     file format elf64-x86-64
architecture: i386:x86-64, flags 0x00000011:
HAS_RELOC, HAS_SYMS
start address 0x0000000000000000
```

Манипулировать содержимым библиотечных файлов можно с помощью команды `ar`.
Чтобы добавить или заменить объектный файл в архиве
используется команда `ar r`. Например,

```bash
ar r libsum.a sum.o
```

добавляет в библиотечный файл `libsum.a` или заменяет, если
файл в библиотечном файле уже существовал, файл `sum.o`.

## Видимость символов

На примере программы из предыдущего раздела мы видим,
что имена переменных и функций попадают в таблицу символов
объектного файла и поэтому могут быть использованы из другой единицы
компиляции.

Ограничить видимость переменных и функций можно с помощью
ключевого слова `static`. Например, модифицируем нашу
программу следующим образом.

```c
#include <stdio.h>

static int x = 1;
int y;
static int compute()
{
    return x + y;
}

int main()
{
    [[maybe_unused]] int r = scanf("%d%d", &x, &y);
    printf("%d\n", compute());
}
```

Скомпилируем программу до объектного кода и выведем таблицу символов
объектного файла.

```
0000000000000000 l    df *ABS*  0000000000000000 sum2.c
0000000000000000 l    d  .text  0000000000000000 .text
0000000000000000 l    d  .data  0000000000000000 .data
0000000000000000 l     F .text  000000000000000d compute
0000000000000000 l     O .data  0000000000000004 x
0000000000000000 l    d  .rodata.str1.1 0000000000000000 .rodata.str1.1
0000000000000000 l    d  .text.startup  0000000000000000 .text.startup
0000000000000000 g     O .bss   0000000000000004 y
0000000000000000 g     F .text.startup  0000000000000036 main
0000000000000000         *UND*  0000000000000000 __isoc99_scanf
0000000000000000         *UND*  0000000000000000 printf
```

Идентификаторы `compute` и `x` из глобальных ('g') превратились в локальные `l'.
Локальные идентификаторы недоступны для других единиц трансляции.
По этой причине функция `main` не может быть `static`.

Ключевое слово `static` при определении переменной задаёт _статический класс памяти_.
Эта глобальная переменная существует всё время работы программы, но идентификатор
переменной недоступен для связывания из других единиц трансляции.
Конечно же, это не запрещает взять адрес переменной и передавать этот
адрес в другие единицы трансляции, речь идет о видимости переменных на этапе компоновки.

Второе использование ключевого слова `static` &mdash; для переменных внутри блока.

```c
int count_me()
{
    static int count;
    return count++;
}
```

Переменная `count` видна только внутри блока функции `count_me`.
Видимость переменной означает, что использование идентификатора `count`
в программе будет означать использование этой переменной.
То есть переменную `count` вне тела функции использовать нельзя,
она там не видна. Но память под эту переменную выделена всё время
работы программы, от момента старта до момента завершения.
Значение переменной сохранится между вызовами функции `count_me`.
Получается, что переменная `count` хранит количество вызовов
функции `count_me`.

Если мы компилируем so-файл (динамическую библиотеку),
по умолчанию все глобальные переменные и функции будут добавлены
в динамическую таблицу символов и будут доступны для использования
извне динамической библиотеки. Чтобы ограничить «протекание»
переменных или функций вовне динамической библиотеки
в ELF-файле есть специальный тип видимости "hidden".
К сожалению, его нет в языке C, поэтому чтобы использовать
тип видимости hidden нужно либо задавать опции командной строки
компилятора, либо использовать в тексте программы
расширения языка C, специфичные для компилятора.

Пусть в динамической библиотеке

```c
int x = 1, y;
int compute()
{
    return x + y;
}
```

мы хотим, чтобы переменные `x` и `y` были недоступны извне библиотеки.

Скомпилируем библиотеку с флагом `-fvisibility=hidden`.

```bash
gcc sum3.c -fPIC -shared -osum3.so -fvisibility=hidden
```

Этот флаг обозначает, что все глобальные идентификаторы будут доступны
компоновщику при сборке so-файла, но из динамической таблицы символов будут удалены.
Динамическая таблица символов будет выглядеть примерно так:

```
sum3.so:     file format elf64-x86-64

DYNAMIC SYMBOL TABLE:
0000000000000000  w   D  *UND*  0000000000000000  Base        _ITM_deregisterTMCloneTable
0000000000000000  w   D  *UND*  0000000000000000  Base        __gmon_start__
0000000000000000  w   D  *UND*  0000000000000000  Base        _ITM_registerTMCloneTable
0000000000000000  w   DF *UND*  0000000000000000 (GLIBC_2.2.5) __cxa_finalize
```

переменные `x`, `y` и функция `compute` в ней отсутствуют, следовательно,
они не могут быть использованы извне so-файла.
Теперь мы хотим сделать функцию `compute` видимой динамически.

Для этого воспользуемся директивой `#pragma`.

```c
int x = 1, y;

#pragma GCC visibility push(default)
int compute()
{
    return x + y;
}
#pragma GCC visibility pop
```

Директива `#pragma GCC visibility push(default)`
запоминает текущую видимость глобальных идентификаторов в стеке
и устанавливает ее в значение `default` &mdash; стандартное. Теперь
динамическая таблица символов станет такой:

```
sum3.so:     file format elf64-x86-64

DYNAMIC SYMBOL TABLE:
0000000000000000  w   D  *UND*  0000000000000000  Base        _ITM_deregisterTMCloneTable
0000000000000000  w   D  *UND*  0000000000000000  Base        __gmon_start__
0000000000000000  w   D  *UND*  0000000000000000  Base        _ITM_registerTMCloneTable
0000000000000000  w   DF *UND*  0000000000000000 (GLIBC_2.2.5) __cxa_finalize
00000000000010f9 g    DF .text  0000000000000014  Base        compute
```

в ней появилась функция `compute`, чего мы и добивались.

## Интероперабельность с другими языками

В данном разделе мы рассмотрим, как единицы трансляции на языке C можно использовать в одной программе с единицами трансляции на других языках.

### Интероперабельность с языком C++

Языки C и C++ имеют общую модель исполнения и очень большое общее подмножество. Многие программы на C являются корректными программами на C++.

Рассмотрим такой код на языке C++ (`work.cpp`).

```c++
#include <iostream>

struct Interop;

extern "C" void handle_in_c(Interop *obj);
struct Interop
{
    int val1_;
    double val2_;

    Interop(int val1, double val2) : val1_{val1}, val2_{val2} {}
    void print() const noexcept;
    void work()
    {
        handle_in_c(this);
    }
};

void Interop::print() const noexcept
{
    std::cout << "val1: " << val1_ << ", val2: " << val2_ << std::endl;
}

extern "C" Interop *create(int val1, double val2);
Interop *create(int val1, double val2)
{
    return new Interop{val1, val2};
}

extern "C" long long work(Interop *obj);
long long work(Interop *obj)
{
    obj->work();
    long long res = obj->val1_ + obj->val2_;
    delete obj;
    return res;
}
```

Функция `handle_in_c` объявляется как использующая соглашение именования языка C (`extern "C"`); она не определена в этом файле, а в другом файле она может быть определена как на языке C, так и на другом языке, который поддерживает соглашения о
именовании C. Структура `Interop` в терминах языка C++ является структурой с тривиальным размещением (trivial layout type). Для структур с тривиальным размещением гарантируется совместимость с языком C.
Функции `create` и `work` объявлены как использующие соглашения об именовании C, но определенные в этом же файле и написанные на C++. Чтобы понять, как отличается именование функций в C и C++, можно посмотреть на таблицу символов объектного файла
с помощью команды `nm work.o`. Получим примерно следующее (часть строк из вывода удалена):

```
000000000000007e T create
                 U handle_in_c
00000000000000bf T work
0000000000000000 W _ZN7Interop4workEv
0000000000000000 T _ZNK7Interop5printEv
```

Видно, что для функций, объявленных с помощью `extern "C"`, их имя в объектном файле совпадает с именем в программе на C++.
А для функций-членов структуры `work` и `print` их имя в объектном файле сильно отличается.
В языке C++ при вызове функции нужно учитывать, какие у нее параметры, в каком пространстве имен или классе она определена и многое другое.
Поскольку компоновщик ничего не знает о типах параметров и пространствах имен языка C++, вся информация, необходимая, чтобы однозначно
идентифицировать функцию, кодируется в ее имени. Говорят, что имя функции декорируется и компоновщик работает с декорированными (mangled)
именами функций. Де-декорированные (demangled) имена функций можно вывести с помощью команды `nm --demangle work.o`.

```
000000000000007e T create
                 U handle_in_c
00000000000000bf T work
0000000000000000 W Interop::work()
0000000000000000 T Interop::print() const
```

Теперь посмотрим на второй файл с исходным кодом на C (`main.c`).

```c
#include <stdio.h>

struct Interop;

struct Interop *create(int val1, double val2);
long long work(struct Interop *obj);
void _ZNK7Interop5printEv(struct Interop *self);

struct Interop
{
    int val1_;
    double val2_;
};

void handle_in_c(struct Interop *obj)
{
    obj->val1_ += 100;
    _ZNK7Interop5printEv(obj);
}

int main()
{
    int x;
    double y;

    [[maybe_unused]] int r = scanf("%d%lf", &x, &y);
    struct Interop *obj = create(x, y);
    obj->val2_ += 500;

    work(obj);
}
```

Мы объявляем функции `create` и `work` пользуясь тем, что в программе на C++ они объявлены с соглашением по именованию C, поэтому их имена в программах на C и C++ совпадают.
Мы объявляем функцию `_ZNK7Interop5printEv` по ее декорированному имени (это `Interop::print()`).
Структура `Interop` объявляется как в C++, но без конструктора и методов. Тривиальное размещение полей гарантирует совпадение размещения в C и C++ (если порядок полей и их типы совпадают, естественно).
Функция `handle_in_c` вызывает метод `Interop::print()` по его декорированному имени, передавая указатель `this` в качестве явного первого параметра функции.

Скомпилировать программу с одной единицей трансляции на языке C и с другой единицей трансляции на C++ можно командой

```bash
gcc main.c work.cpp  -lstdc++ -omain
```

Мы указываем, что при компоновке необходимо использовать стандартную библиотеку языка C++ (`-lstdc++`), из которой должны быть взяты операции вывода, использующиеся в файле на C++.
Результат компиляции будет находиться в файле `main`.
