# Библиотеки

## Указатели на функции

Декларатор вида:

```c
int (*pfunc)(int a, int b);
```

читается следующим образом: `pfunc` &mdash; это указатель на функцию, принимающую два параметра типа `int` и возвращающую значение типа `int`.
То есть `pfunc` &mdash; это переменная _указатель на функцию_. С помощью `typedef` переменная может быть объявлена следующим образом:

```c
typedef int (*func_t)(int a, int b); // func_t - тип указателя на функцию
func_t pfunc;
```

Любая переменная-указатель на функцию может принимать значение `NULL` (или 0, или `nullptr` в Си++).
Если переменная-указатель на функцию не равна `NULL`, она должна _указывать на_ функцию,
совместимую по передаваемым параметрам и возвращаемому значению.

Операция взятия адреса `&`, примененная к имени функции, дает значение типа указателя на функцию
с соответствующим количеством и типом параметров и типом возвращаемого значения, например:

```c
int handler(int value, int mask);

    &handler   // даст значение типа int (*)(int, int)
```

Однако, для имен функций автоматически выполняется неявное преобразование имени функции в указатель на функцию.
То есть,

```c
pfunc = handler;
```

это то же самое, что

```c
pfunc = &handler;
```

Поэтому, как правило, явную операцию взятия адреса перед именами функций не пишут.

Операция разыменования `*`, примененная к указателю NULL или к указателю, не указывающему на функцию,
совместимую по передаваемым параметрам и возвращаемому значению, дает **неопределенное поведение**
(undefined behavior). Как обычно, компилятор имеет право исходить из предположения, что в программе
при ее выполнении никогда не возникает неопределённое поведение, и оптимизировать программу соответственно.

Если указатель на функцию корректен, то операция разыменования дает в результате значение (точнее, function designator),
к которому применима операция вызова функции. Например,

```c
    int z = (*pfunc)(10, 20);   // будет вызвана функция, на которую в данный момент указывает pfunc
```

Если указатель на функцию используется там, где требуется function designator, он неявно разыменовывается. Таким образом,
явная операция `*` для вызова функции по указателю не нужна и часто опускается.

```c
    int z = pfunc(10, 20);     // то же, что и выше
```

Поэтому по виду операции вызова функции бывает сложно определить, вызывается ли функция напрямую или через указатель.

### Использование указателей на функции

Указатели на функции требуются в реализациях обобщенных алгоритмов. Например, рассмотрим функцию сортировки стандартной
библиотеки языка C:

```c
void qsort(void *base, size_t nmemb, size_t size, int (*compar)(const void *, const void *));
```

Функция `qsort` сортирует массив данных, расположенный в памяти по указателю `base` и содержащий `nmemb` элементов.
Размер одного элемента задается параметром `size`. При выполнении сортировки для сравнения элементов массива будет
вызываться функция сортировки, указатель на которую передается в параметре `compar`. Этой функции сортировки
будут передаваться указатели на два элемента сортируемого массива, и функция сортировки должна вернуть 0, если элементы равны,
отрицательное значение, если первый элемент массива меньше второго, и положительное значение, если первый элемент массива
больше второго. Функция `qsort` может реализовывать нестабильную сортировку, то есть в отсортированном массиве не гарантируется,
что равные элементы сохранят свой относительный порядок.

Предположим, что требуется отсортировать массив целых чисел в порядке неубывания.

```c
void sort_ints(int *data, int count);
```

Функция принимает параметр `data`, указывающий на начало сортируемого массива, и параметр `count`, содержащий число сортируемых элементов массива.
Тогда вызов функции `qsort` может быть записан следующим образом:

```c
void sort_ints(int *data, int count)
{
    qsort(data, // указатель на начало сортируемых данных, к void * преобразуется автоматически
          count, // количество элементов в сортируемом массиве
          sizeof(data[0]), // размер одного элемента массива
          sort_func); // функция сортировки, см. ниже
}
```

Предположим, что в процессе сортировки потребовалось выполнить сравнение элементов `data[i]` и `data[j]`, где `i` и `j` &mdash; некоторые индексы.
Тогда будет вызвана функция сравнения, указатель на которую был передан в параметре `sort_func`, и ей в качестве аргументов будут
переданы указатели на сравниваемые значения, то есть `&data[i]` и `&data[j]`. Функция сравнения может быть написана
следующим образом:

```c
int sort_func(const void *arg1, const void *arg2)
{
    int val1 = *(const int*) arg1; // требуется явное преобразование из const void * в const int *
    int val2 = *(const int*) arg2;
    // помним, что int может переполняться при вычитании!
    if (val1 < val2) {
        return -1;
    } else {
        return val1 > val2;
    }
}
```

При написании функции сравнения может возникнуть идея написать нужные типы аргументов в функции `sort_func`, а в вызов `qsort` добавить
явное преобразование типа:

```c
int sort_func(const int *arg1, const int *arg2)
{
    if (*arg1 < *arg2) {
        return -1;
    } else {
        return *arg1 > *arg2;
    }
}
void sort_ints(int *data, int count)
{
    qsort(data, // указатель на начало сортируемых данных, к void * преобразуется автоматически
          count, // количество элементов в сортируемом массиве
          sizeof(data[0]), // размер одного элемента массива
          (int (*)(const void *, const void *)) sort_func);
}
```

**Это &mdash; плохая, нет, очень плохая идея!**
В этом случае явное преобразование типа в вызове `qsort` скроет возможное рассогласование между фактическими параметрами
функции `sort_func` и параметрами, передаваемыми ей функцией `qsort`. Не делайте так!

### Передача пользовательского контекста

Функция, которая передается в качестве аргумента в другую функцию для того, чтобы быть вызванной позже при наступлении
какого-либо условия, называется _функцией обратного вызова_ (callback function). Например, гипотетическая
функция установки таймера может требовать функции, которая будет вызвана при истечении указанного интервала времени.

```c
void timer_handler(void)
{
}

// использование:
    set_timer(1000, timer_handler);  // таймер устанавливается на 1000 миллисекунд, затем вызывается timer_handler
```

Сложности, возникающие из-за того, что функция `timer_handler` может быть вызвана _асинхронно_, то есть
в непредсказуемый для основной программы момент, мы рассмотрим в дальнейшем, пока же остановимся на передаче дополнительной
информации в функцию обратного вызова.

Функция обратного вызова `timer_handler` может требовать для своей работы дополнительной информации, например, о том,
как обрабатывать тайм-аут. Поскольку наш вариант `timer_handler` не принимает никаких параметров, дополнительная
информация может быть передана этой функции только в глобальных переменных, что не является хорошим решением.
Использование глобальных переменных делает сложным ее распараллеливание на несколько нитей, затрудняет ее поддержку и модификацию.

Поэтому, как правило, во всех функциях, которые принимают в качестве параметра указатель на функцию обратного вызова,
принимается и дополнительный параметр `user` типа `void *`. Этот параметр без изменений передается в функцию обратного вызова.

Например:

```c
struct TimerContext
{
    // здесь необходимые данные для обработки тайм-аута
};

void timer_handler(void *user)
{
    struct TimerContext *cntx = user;
    // обрабатываем тайм-аут с данными в cntx
}

// основная программа
    struct TimerContext cntx = { /* задаем доп. информацию для обработчика тайм-аута */ };
    set_timer(1000, timer_handler, &cntx); // передаем ее в обработчик, когда он будет вызван
```

### Сортировка с передачей контекста

Функция `qsort`, описанная выше, выполняет сортировку массива, используя заданную функцию
сравнения. Но эта функция сравнения принимает только два указателя на сравниваемые значения,
не позволяя передавать дополнительный контекст. Эта недоработка устранена в функции
`qsort_r`.

```c
typedef int (*compar_func_t)(const void *p1, const void *p2, void *arg);
void qsort_r(void *base, size_t n, size_t size, compar_func_t compar, void *arg);
```

Функция сравнения для функции сортировки принимает три параметра вместо двух.
Функция сортировки получает дополнительный параметр `arg`, который передаётся
в функцию сравнения.

Функция `qsort_r` не является стандартной, но доступна в библиотеке glibc
на Linux. Чтобы использовать функцию, надо при компиляции дополнительно указать
опцию командной строки `-D_GNU_SOURCE`.

## Полиморфизм в C

Полиморфным вызовом функции называется операция вызова функции, которая в зависимости
от точки в программе или от текущего состояния программы вызывает разные реализации,
то есть разные тела функции. То есть один и тот же идентификатор функции в программе
означает разные вещи.

Полиморфизм бывает _параметрический_, _специализированный_ (ad-hoc) и _подтиповой_.

Параметрический полиморфизм позволяет определять обобщённые функции или типы данных,
когда один и тот же текст позволяет обрабатывать значения разных типов.
В языке C параметрический полиморфизм реализуется с помощью макросов,
в языке C++ добавляются шаблонные функции или типы данных. В других языках
та же функциональность называется обобщенными функциями (generic function) или типами
данных.

Специализированный полиморфизм (иногда называют его статическим полиморфизмом)
заключается либо в перегрузке операций, когда один и тот же знак операции
может обозначать совершенно разные операции, либо в перегрузке функций,
когда в зависимости от типа параметров могут вызываться текстуально разные реализации
функций. Этот вид полиморфизма тоже есть C в ограниченной форме. Например,
операция `+` в программе может вызывать совершенно разные операции в случае,
если аргументы целые или вещественные числа. Язык C даже поддерживает ограниченную
форму перегрузки функций с помощью Generic-макросов.

Подтиповой полиморфизм реализуется в С++ в форме _динамического_ полиморфизма,
когда вызов функции, объявленной в классе виртуальной, диспетчеризуется
на конкретную реализацию уже при работе программы. В языке C тоже возможна реализация
динамического полиморфизма, она будет более низкоуровневой и будет использовать
указатели на функции.

Далее мы реализуем концепцию динамического полиморфизма на языке C.
Рассмотрим модельную задачу представления сцен двухмерных фигур.
Мы будем поддерживать эллипсы, прямоугольники и треугольники.
Эллипс будет задаваться координатами центра и двумя полуосями,
причем полуоси должны быть параллельны осям координат.
Прямоугольник будет задаваться координатами двух противоположных углов,
мы будем поддерживать только прямоугольники, ориентированные вдоль осей координат.
Треугольник будет задаваться координатами своих углов.
Мы хотим, чтобы двухмерная фигура поддерживала следующие операции:

```c
// прямоугольник-рамка для фигуры
typedef struct BoundingBox
{
    double x1, y1, x2, y2;
} BoundingBox;

typedef struct Figure
{
    // TODO
} Figure;

// освободить память, занимаемую фигурой
void figure_free(Figure *);
// вычислить площадь
double figure_square(const Figure *);
// вычислить bounding box
BoundingBox figure_bbox(const Figure *);
```

Мы предполагаем, что объект фигуры будет создаваться в динамической памяти, поэтому функция
`figure_free` должна освободить память, занимаемую структурой, и, возможно, освободить
память во внутренних указателях, если они нам понадобятся.
Саму структуру `Figure` мы будем определять, чтобы поддерживались все требуемые операции.

Один из возможных вариантов реализации &mdash; определить перечислимый тип для всех
поддерживаемых типов фигур, и в каждой функции реализовать обработку всех поддерживаемых типов.
То есть, мы определяем перечислимый тип:

```c
typedef enum FigureType { RECTANGLE, ELLIPSE, TRIANGLE } FigureType;

typedef struct Figure
{
    FigureType ft;
    // все необходимые поля для всех фигур
} Figure;
```

То есть структура `Figure` будет содержать все необходимые поля для всех поддерживамых типов фигур.
Мы можем даже использовать тип `union`, чтобы сэкономить немного памяти. А код функции `figure_square`
будет содержать `switch` по всем поддерживаемым типам фигур:

```c
double figure_square(const Figure *f)
{
    switch (f->ft) {
    case RECTANGLE: // вычисляем площать прямоугольника
        return square_of_rectangle;
    case ELLIPSE:   // вычисляем площадь эллипса
        return square_of_ellipse;
    case TRIANGLE:  // вычисляем площадь треугольника
        return square_of_triangle;
    default:        // что-то пошло не так
        abort();
    }
}
```

Это, возможно, и не плохая реализация. У нее есть недостаток, что если мы хотим добавить новую фигуру,
нам потребуется добавить обработку нового типа фигуры в несколько мест программы. Список поддерживаемых фигур
закрыт, чтобы добавить новую фигуру потребуется перекомпиляция всей программы.

Мы применим другой подход, основанный на таблице функций в объекте фигуры. Итак, у нас есть три операции,
которые должны поддерживаться каждой фигурой. Определим структуру с указателями на функции, соответствующие
трём поддерживаемым операциям:

```c
struct Figure; // forward declaration, мы хотим использовать указатель на Figure
typedef struct FigureOps
{
    void (*free)(struct Figure *);              // указатель на функцию освобождения ресурсов
    double (*square)(const struct Figure *);    // указатель на функцию вычисления площади
    BoundingBox (*bbox)(const struct Figure *); // указатель на функцию вычисления bounding box
} FigureOps;
```

Структура `Figure` будет содержать только указатель на структуру операций:

```c
typedef struct Figure
{
    const FigureOps *ops;   // сами указатели изменяться не будут
} Figure;
```

Функции работы с фигурой будут просто вызывать функцию по указателю из структуры операций:

```c
double figure_square(const Figure *f)
{
    return f->ops->square(f);
}
```

Таким образом мы фактически определили абстрактный класс или интерфейс. Он не содержит никакой реализации
функциональности для фигур, но задаёт набор операций, который должна реализовывать каждая конкретная фигура.
При этом у типа `Figure` вообще нет никакой информации ни о полях данных, необходимых для реализации
каждого конкретного типа фигур, ни реализации требуемых операций.

Теперь нужно определить типы фигур. Например, тип для прямоугольника можно определить так:

```c
typedef struct Rectangle
{
    Figure b;
    double x1, y1, x2, y2;
} Rectangle;
```

Здесь важно, что первым полем у структуры `Rectangle` является поле _базового_ типа `Figure`.
Это принципиально и позволяет выполнять преобразования типа между разными структурными типами.

Функция вычисления площади для прямоугольника будет такой:

```c
static double rect_square(const Figure *f)
{
    const Rectangle *r = (const Rectangle *) f;
    return fabs(r->x2 - r->x1) * fabs(r->y2 - r->y1);
}
```

Функция `rect_square`, хотя фактически работает с указателем на тип `Rectangle` должна принимать
указатель на `Figure`, чтобы соответствовать типу указателя на функцию поля `square`
структуры `FigureOps`. Поэтому первая операция, которая выполняется в теле функции `rect_square` &mdash;
это преобразование указателя на базовую структуру `Figure` к указателю на структуру `Rectangle`.

Функции `rect_free` и `rect_bbox` определяются по аналогии. В итоге у нас есть реализации
всех необходимых операций для прямоугольника, и теперь мы можем определить экземпляр
структуры операций для прямоугольника.

```c
static const RectangleOps rect_ops =
{
    rec_free,
    rec_square,
    rec_bbox,
}
```

Нам осталось написать функцию _конструктор_, которая будет создавать новый объект прямоугольника.
Она может быть такой:

```c
Figure *rectangle_new(double x1, double y1, double x2, double y2)
{
    Rectangle *r = calloc(1, sizeof(*r));  // calloc лучше, так как обнуляет память
    r->b.ops = rect_ops;  // инициализируем указатели на операции
    r->x1 = x1; r->y1 = y1; r->x2 = x2; r->y2 = y2;
    return &r->b; // возвращаем указатель на базовый тип Figure
}
```

Но для всех наших типов (прямоугольник, эллипс, треугольник) у конструкторов будет разный список
параметров, что не удобно для унификации создания фигур, которая нам потребуется дальше.
Поэтому определим конструктор из строки. Сигнатура конструктора из строки не зависит от создаваемого
объекта, поэтому все конструкторы фигур имеют одинаковый прототип.

```c
Figure *rectangle_from_str(const char *s)
{
    double x1, y1, x2, y2;
    sscanf("%lf%lf%lf%lf", &x1, &y1, &x2, &y2); // TODO: проверить корректность преобразования
    return rectangle_new(x1, y1, x2, y2);
}
```

Проверку на ошибки выделения памяти и ошибки преобразования из строки в число мы оставляем
в качестве упражнения. Так определяются функции `rectangle_from_str`, `ellipse_from_str`,
`triangle_from_str`, которые создают объекты соответствующего типа из строки.

Теперь мы можем написать первый вариант функции _фабрики_ типов для создания фигуры
любого поддерживаемого типа. Фабрика принимает строку, выделяет из неё первое слово,
которое должно быть `rectangle`, `ellipse` или `triangle`, и в зависимости от слова
вызывает соответствующую функцию-конструктор.

```c
typedef struct SupportedFigures
{
    const char *name;
    Figure * (*from_str)(const char *s);
} SupportedFigures;
// таблица поддерживаемых типов фигур
static const SupportedFigures supported[] =
{
    { "rectangle", rectangle_from_str },
    { "ellipse", ellipse_from_str },
    { "triangle", triangle_from_str },
};
Figure *figure_from_str(const char *s)
{
    char *ft = NULL;
    int n;
    if (sscanf(s, "%ms%n", &ft, &n) != 1) {
        // TODO: report error
        return NULL;
    }
    for (size_t i = 0; i < sizeof(supported) / sizeof(supported[0]); ++i) {
        if (!strcmp(supported[i].name, ft)) {
            Figure *f = supported[i].from_str(&s[n]);
            free(ft);
            return f;
        }
    }
    // TODO: report error
    free(ft);
    return NULL;
}
```

### Функции инициализации в единицах трансляции

Фабрика объектов, реализованная выше в функции `figure_from_str`, имеет один небольшой недостаток.
В ней в массиве `supported` при компиляции программы перечислены все типы фигур,
которые поддерживаются в программе. Если в программу потребуется добавить новый поддерживаемый тип
фигур, то информацию о нём нужно будет дописать в массив `supported` и перекомпилировать
программу.

Мы заменим статическую конфигурацию программы, то есть конфигурацию при компиляции программы,
на динамическую конфигурацию. Для этого нужно отказаться от константного массива `supported`
и реализовать добавление записей (по-сути регистрацию) во время работы программы.
Для этого потребуется реализовать функцию `figure_register`:

```c
void figure_register(const char *name, Figure * (*from_str)(const char *s))
{
    // функции передаются имя типа объекта name и функция создания объекта from_str
    // функция figure_register должна сохранить переданную информацию о регистрации
    // в динамически расширяемый массив supported
    // Продвинутый вариант: использовать хеш-таблицу
}
```

Функция `figure_from_str` теперь должна работать с новой структурой данных регистрации.

```c
Figure *figure_from_str(const char *name)
{
    // ищем по расширяемому массиву имя типа name и вызываем функцию создания
    // в продвинутом варианте ищем по хеш-таблице
}
```

Теперь, чтобы функция `figure_register` была вызвана автоматически,
можем воспользоваться расширением C, которое поддерживается и gcc и clang
и которое позволяет указывать в единице трансляции функции, которые будут
вызваны автоматически при загрузке программы в память. Например, для
прямоугольника в файле `rectangle.c` допишем функцию

```c
static __attribute__((constructor)) void init() {
    figure_register("rectangle", rectangle_from_str);
}
```

Здесь `__attribute__((constructor))` как раз указывает, что функция
должна быть вызвана автоматически при загрузке программы в память.
Порядок вызова функций инициализации из разных единиц трансляции
одной программы не специфицирован. Скорее всего, это будет тот порядок,
в котором объектные файлы были переданы компоновщику для получения исполняемого файла.
Компилятор C++ использует эту возможность для задания конструкторов,
которые должны быть вызваны для глобальных объектов в программе на C++.

## Статические библиотеки

Статические библиотеки уже рассматривались нами ранее. Статическая библиотека &mdash; это
архив объектных файлов и индекс экспортируемых из объектных файлов символов. При необходимости
объектные файлы могут быть извлечены из статической библиотеки для использования в компоновке
напрямую или в составе других библиотек.

В POSIX-совместимых системах статическая библиотека с именем NAME хранится в файле `libNAME.a`.
Например, если библиотека называется `figures`, она будет хранится в файле `libfigures.a`.
Для сборки статической библиотеки из набора объектных файлов используется команда

```bash
ar rs LIB OBJECTS
```

`LIB` &mdash; это имя выходного файла-библиотеки, `OBJECTS` &mdash; список объектных файлов.
Например, для сборки статической библиотеки `libfigures.a` можно использовать команду

```bash
ar rvs libfigures.a figure.o rectangle.o ellipse.o triangle.o
```

Чтобы подключить библиотеку к программе при её финальной компоновке нужно указать имя библиотеки
в опции `-l` компоновщика. Опция `-l` должна идти после всех компонуемых объектных файлов,
иначе эффекта не будет. Дополнительно может потребоваться указать опцию `-L`, которая позволяет
задавать пути к каталогам, в которых находятся библиотечные файлы. Поэтому чтобы скомпоновать
программу из объектного файла `main.o` и библиотеки `libfigures.a`, находящейся в текущем каталоге,
потребуется следующая командная строка gcc:

```bash
gcc -L. main.o -omain -lfigures
```

Здесь `-L.` добавляет текущий каталог в список каталогов, в которых выполняется поиск библиотек,
`-omain` задаёт имя исполняемого файла-результата, `-lfigures` добавляет в список библиотек
библиотеку `libfigures.a`.

Компоновщик в POSIX-совместимых операционных системах однопроходный, он просматривает
список объектных файлов и библиотек один раз слева направо. Когда компоновщик встречает
статическую библиотеку, он подключает к исполняемой программе только те объектные
файлы из состава статической библиотеки, в которых определяются (экспортируются) символы,
которые импортируются в уже рассмотренные объектные файлы. Если позднее появится объектный файл,
импортирующий символ из данной библиотеки, который был ранее не добавлен в исполняемый файл,
компоновщик не вернётся к уже рассмотренной библиотеке. Поэтому иногда в командной строке
компоновки исполняемой программы встречаются повторения одной и той же библиотеки несколько раз,
например, `-llib1 -llib2 -llib1 -llib2`.

Если собрать в статическую библиотеку файлы, которые используют не явные зависимости
в таблице `supported`, а динамическую регистрацию типов с помощью функций инициализации,
окажется, что в исполняемую программу не будет добавлено ни одной реализации типа фигуры.
Дело в том, что объектный файл `figures.o` не импортирует ни одного символа, относящегося
к реализациям фигур. Чтобы принудить компоновщик добавить в исполняемую программу
все объектные файлы из статической библиотеки, можно использовать опцию компоновщика
`--whole-archive`, включив её перед соответствующей библиотекой и выключив после неё.

```bash
gcc -L. main.o -omain -Wl,--whole-archive -lfigures -Wl,--no-whole-archive
```

Здесь опция `-Wl,OPT` компилятора gcc (и clang тоже) обозначает, что опцию `OPT` нужно
передать компоновщику без изменений.

## Компонуемая динамическая библиотека

Если статическая библиотека &mdash; это архив объектных файлов, из которого компоновщик
берёт объектные файлы, требуемые для компоновки программы, динамическая библиотека, или
разделяемый объектный файл (shared object) &mdash; это полноценно скомпонованная программа,
только без точки входа и функции `main`. То есть динамическая библиотека должна быть
скомпонована из объектных файлов и/или статических библиотек.

Объектные файлы, которые войдут в состав динамической библиотеки, должны быть скомпилированы
со специальными флагами. Дело в том, что динамическая библиотека должна поддерживать
загрузку в память программы с произвольного адреса. Машинный код, который может быть
загружен в память по любому адресу, называется _позиционно-независимым_. Как позиционная
независимость реализуется на разных аппаратных платформах, мы рассмотрим далее в курсе.
При компиляции объектных файлов требуется указать опции `-fPIC -DPIC`. Опция `-fPIC`
включает в компиляторе режим генерации позиционно-независимого кода, а опция `-DPIC`
определяет макрос `PIC`, который может использоваться в стандартных заголовочных файлах.

Поэтому для компиляции, например, файла `figures.o` потребуется следующая командная строка:

```bash
gcc -Wall -Werror -O2 -g -std=gnu23 -fPIC -DPIC -c figure.c
```

Имя объектного файла в командной строке явно не указано, поэтому будет использоваться `figure.o`.

При компоновке динамической библиотеки вместо генерации исполняемого файла должна
генерироваться динамическая библиотека. За это отвечает опция `-shared`. Потребуется
примерно такая командная строка:

```bash
gcc -shared -fPIC -Wall -Werror -O2 -g -std=gnu23 figure.o rectangle.o ellipse.o triangle.o -olibfigures.so
```

Файл с разделяемой библиотекой называется `libfigures.so` по аналогии с `libfigures.a`.

Теперь эту динамическую библиотеку можно прикомпоновать к основной программе почти точно так же,
как в случае использования статической библиотеки.

```bash
gcc -L. -Wall -Werror -O2 -g -std=gnu23 main.o -lfigures -omain
```

Компоновщик найдет в текущем каталоге (`-L.`) файл libfigures.so и автоматически прикомпонует
этот файл динамически. Если есть и `.a` и `.so` файл компоновщик отдаст предпочтение
разделяемой библиотеке (`.so`-файлу), если только динамическая компоновка не запрещена
с помощью `-static`.

Однако попытка запуска этой программы завершится ошибкой.

```
$ ./main
./main: error while loading shared libraries: libfigures.so: cannot open shared object file: No such file or directory
```

Дело в том, что опция `-L.` указывающая каталоги, в которых нужно искать библиотеки для
компоновки, работает только на этапе компоновки, и информация о расположении
динамических библиотек при компоновке не попадает в исполняемый файл.
При запуске программы нужно отдельно указать каталоги, в которых должна искаться
динамическая библиотека для загрузки в память, при этом текущий каталог, конечно же,
в список путей по умолчанию не входит.

Один из вариантов решения проблемы &mdash; установить при запуске программы переменную
окружения `LD_LIBRARY_PATH`, например следующим образом:

```bash
LD_LIBRARY_PATH=. ./main
```

Здесь переменная окружения `LD_LIBRARY_PATH` устанавливается в текущий каталог только для
запуска программы `./main`.

Другой вариант решения проблемы &mdash; добавить в исполняемый файл информацию о том,
где можно найти требуемую динамическую библиотеку, с помощью опции компоновщика `-rpath`.

```bash
gcc -L. -Wall -Werror -O2 -g -std=gnu23 main.o -lfigures -Wl,-rpath -Wl,'$ORIGIN' -omain
```

Запись `$ORIGIN`, добавленная в исполняемый файл, задаёт, что динамические библиотеки
должны искаться в том каталоге, из которого был запущен сам исполняемый файл.

## Динамическая подгрузка библиотек

В предыдущем примере действия по подгрузке требуемой динамической библиотеки в память процесса,
нахождению в ней требуемых функций и связыванию функции из динамической библиотеки с точкой вызова
в основной программе выполняются динамическим загрузчиком. Это удобно,
когда имена библиотек и функций известны на этапе компиляции и не меняются динамически,
например при использовании стандартной библиотеки C.
Как правило, динамическое связывание основной программы и стандартных библиотек используется
по умолчанию.

Однако если имя динамически подгружаемой библиотеки или имя функции в ней неизвестно на этапе
компиляции и определяется на этапе работы программы (берется из конфигурационных файлов
или из ввода пользователя), динамическая компоновка средствами компилятора не применима.
Тогда нужно использовать библиотечные средства для загрузки библиотек и поиска имен в них.

В стандарте POSIX библиотечные функции для динамической загрузки определены в библиотеке dl.
Для их использования необходимо подключить заголовочный файл `dlfcn.h`.

```c
#include <dlfcn.h>
```

Функции работы с динамическим загрузчиком не находятся в составе стандартной библиотеки libc, а вынесены
в отдельную библиотеку libdl. Поэтому при компоновке программы необходимо добавить опцию `-ldl`
для подключения этой библиотеки. Командная строка компоновки может выглядеть
следующим образом:

```bash
gcc main.o -omain -ldl
```

Концептуально при использовании библиотеки libdl каждая подгружаемый динамически модуль рассматривается
как некоторый ресурс, работа с которым ведется по модели "открыть-использовать-закрыть" (аналогично файлам,
каталогам и т. п.).

Динамически подгружаемый модуль загружается в память (т. е. "открывается") с помощью функции `dlopen`.

```c
void *dlopen(const char *filename, int flags);
```

Первый параметр `filename` &mdash; это имя файла, содержащего подгружаемый модуль. Если имя файла содержит '/',
оно интерпретируется как абсолютный или относительный путь к загружаемому модулю. Иначе для поиска модуля
используются значение переменной окружения `LD_LIBRARY_PATH`, список путей
вкомпилированный в исполняемый файл с помощью опции `-rpath` и системный список каталогов. Абсолютное имя
файла должно точно указывать на загружаемый модуль. Суффикс имени `.so` (на ELF-системах) можно не указывать, но
можно и указывать.

Параметр `flags` позволяет указать различные флаги. Должен быть указан либо флаг `RTLD_LAZY`, либо флаг `RTLD_NOW`.
`RTLD_LAZY` включает режим отложенного связывания, в котором поиск функции в библиотеке выполняется в момент
первого обращения к ней, а флаг `RTLD_NOW` включает режим немедленного связывания, в котором все действия
по связыванию использования имен с определениями выполняются на этапе загрузки библиотеки. Как правило,
всегда достаточно указать режим `RTLD_LAZY`. Кроме режима открытия в параметре `flags` могут передаваться
дополнительные флаги, объединяемые с помощью операции побитового или (`|`). Описание дополнительных флагов
можно найти в документации на функцию.

В случае ошибки функция `dlopen` возвращает `NULL`,
при этом текстовое сообщение об ошибке можно получить с помощью функции `dlerror`.

В случае успешной загрузки модуля в память процесса функция `dlopen` возвращает "handle" загруженной библиотеки,
некоторый указатель, который нужно передавать в последующие вызовы для работы с данным модулем.
Если модуль уже был загружен в память ранее, будет возвращен ранее созданный "handle", модуль не будет загружаться
второй раз, но счетчик его загрузок будет увеличен на 1. Это означает, в частности, что при повторной загрузке
модуля в память глобальные переменные этого модуля сохранят свои текущие значение, а не будут сброшены в 0.

Информацию об ошибке можно получить с помощью функции `dlerror`.

```c
char *dlerror(void);
```

Функция возвращет NULL, если ошибки не было и текстовую строку описания ошибки в противном случае.
При этом флаг ошибки сбрасывается. Таким образом, второй подряд вызов `dlerror` всегда вернет NULL.
По аналогии с `errno` флаг ошибки не сбрасывается при успешном выполнении функций `dlopen`, `dlsym`
и т. п., поэтому перед первым вызовом `dlopen` имеет смысл вызвать `dlerror` чтобы принудительно
сбросить флаг ошибки.

Модуль "закрывается" с помощью функции `dlclose`.

```c
int dlclose(void *handle);
```

Если счетчик загрузок модуля становится равным 0, он выгружается из памяти.

Найти в загруженном модуле функцию или переменную можно с помощью функции `dlsym`.

```c
void *dlsym(void *handle, const char *symbol);
```

В параметре `handle` передается модуль, в котором нужно искать имя, а в параметре `symbol` &mdash; само имя.
Функция возвращает NULL, если имя не найдено, и указатель на соответствующий объект, если имя найдено.
Возвращенный указатель потребуется явно или неявно привести к типу указателя на функцию,
чтобы его можно быть использовать для вызова.

Таким образом, простейший вариант функции `main`, который использует явную
загрузку динамического модуля libfigures.so может быть таким.

```c
static const char so_file_name[] = "./libfigures.so";
static const char so_func_name[] = "figure_from_str";

int main()
{
    void *handle = NULL;
    Figure * (*create_func)(const char *) = NULL;

    handle = dlopen(so_file_name, RTLD_LAZY);
    if (!handle) {
        fprintf(stderr, "failed to open SO file: %s\n", dlerror());
        exit(1);
    }
    void *func = dlsym(handle, so_func_name);
    if (!func) {
        fprintf(stderr, "failed to lookup %s: %s\n", so_func_name, dlerror());
        exit(1);
    }
    create_func = func;

    // используем create_func для создания объектов

    dlclose(handle);
}
```

## Работа с функциями в самой программе

Основная программа принципиально ничем не отличается от подгружаемых модулей, то есть нам может потребоваться искать адреса
функций или переменных по их именам не только в подгружаемых модулях, но и в основной программе. Работа с именами
в основной программе тоже ведется по схеме "открыть-использовать-закрыть". Чтобы "открыть" основную программу
нужно в параметре filename передать NULL, например:

```c
    mainhandle = dlopen(NULL, RTLD_LAZY);
```

После чего можно искать имена в основной программе:

```c
    mainfunc = dlsym(mainhandle, "main");
```

Однако по умолчанию основная программа компилируется без таблицы имен, доступной для функции `dlsym`,
поэтому функция вернет `NULL`. Чтобы включить генерацию таблицы имен в основную программу
нужно компоновать ее с опцией `-rdynamic`.

```bash
gcc -rdynamic main.o -omain -ldl
```
