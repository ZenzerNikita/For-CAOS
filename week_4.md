## Работа с файлами

Когда программа начинает работу она, как правило, может работать с тремя потоками
для вывода и ввода данных. Они объявляются следующим образом:

```c
FILE *stdin, *stdout, *stderr;
```

Это указатели на структуру данных `FILE`. Внутреннее устройство структуры `FILE`
от нас скрыто, но оно и не требуется, так как программа всегда работает
с указателем на структуру `FILE`. Когда внутреннее устройство структуры
скрыто от пользователя, говорят о «непрозрачных» (opaque) структурах.
Указатель на структуру `FILE` мы будем в дальнейшем называть _дескриптор потока_.

Программа может открывать новые потоки для ввода и вывода, связывая их
с файлами на файловой системе. Основная функция называется `fopen`:

```c
FILE *fopen(const char *path, const char *mode);
```

Аргумент `path` &mdash; это путь к открываемому файлу, а аргумент `mode` &mdash; режим открытия.
Функция `fopen` возвращает дескриптор потока, который в дальнейшем нужно использовать для работы с этим файлом.
Но если операция открытия была неуспешной, то функция вернет нулевой указатель `NULL`.
Результат функции `fopen` должен быть обязательно проверен перед тем, как выполнять дальнейшие операции с файлом.
Например:

```c
#include <stdio.h>
#include <string.h>  // для strerror
#include <errno.h>   // для errno

    const char *path = "input.txt";
    FILE *f = fopen(path, "r");
    if (!f) {
        fprintf(stderr, "%s: failed to open file '%s': %s\n", __FUNCTION__, path, strerror(errno));
        return;
    }
```

В этом примере в случае ошибки выводится сообщение об ошибке, после чего функция завершает работу.
Если данный код выполняется в функции, которая должна возвращать значение, то при ошибке
обычно возвращается специальное значение, сигнализирующее об ошибке.
Хорошее сообщение об ошибке должно удовлетворять следующим требованиям:
* сообщение об ошибке может выводиться в `stderr` либо в специальный лог-файл, но никогда не в `stdout` или другой файл, в который выводятся результаты работы;
* сообщение об ошибке должно завершаться переходом на новую строку `'\n'`;
* сообщение об ошибке должно давать информацию, в каком месте программы произошла ошибка, поэтому используется `__FUNCTION__`, чтобы вывести имя текущей функции;
* сообщение об ошибке должно давать информацию об объекте, при обработке которого произошла ошибка, поэтому выводится `path`;
* сообщение об ошибке должно давать информацию о сути ошибки, поэтому выводится строковое описание кода ошибки, возвращённого операционной системой `strerror(errno)`.

Второй параметр функции `fopen` задаёт режим открытия файла. Три самых частых режима открытия перечислены ниже.

Режим открытия `"r"` &mdash; открытие файла на чтение. Дескриптор потока работает только на чтение, то есть в него
нельзя записывать. Если файл с путём `path` не существовал, функция `fopen` завершается неуспешно.
Для чтения содержимого файла можно использовать функции `getc`, `fgets`, `fscanf`, `getline`
и аналогичные. Это обычный режим для открытия файла со входными данными.

Режим открытия `"w"` &mdash; открытие файла на запись. Дескриптор потока работает только на запись, из него нельзя
читать данные. Если файл с путём `path` не существовал, он создаётся пустым, а если существовал,
то очищается. Для записи в файл можно использовать функции `putc`, `fputs`, `fprintf`
и аналогичные. Это обычный режим для открытия файла для записи результатов работы программы.

Режим открытия `"a"` &mdash; открытие файла на добавление. Дескриптор потока работает только на запись, из
него нельзя читать данные. Если файл с путём `path` не существовал, он создаётся пустым,
но если существовал, то его содержимое сохраняется. Любая операция записи в файл добавляет
данные в конец файла.
Это обычный режим для открытия файлов логов выполнения.

Обратите внимание, что в POSIX-совместимых системах один и тот же файл можно открывать
несколько раз с разными режимами. Будет создано несколько дескрипторов потока,
с помощью которых можно независимо записывать данные в файл и считывать данные из файла.
Более подробно о том, что происходит в таком случае, будет рассказано во второй части нашего курса.

### Буферизация ввода-вывода

По умолчанию потоки ввода-вывода буферизуются. Это значит, что, например, при побайтовом
чтении из потока с помощью `getc` стандартная библиотека попытается заполнить внутренний буфер за одно
обращение к ядру операционной системы (так называемый _системный вызов_), а затем будет
выдавать в качестве результата вызова `getc` по одному байту из буфера. Когда буфер будет
прочитан, стандартная библиотека обратиться к ядру операционной системы за следующей порцией
считываемых данных. При побайтовой записи в поток с помощью `putc` стандартная библиотека
заполняет внутренний буфер, и когда он будет заполнен, данные будут записаны на устройство
за один системный вызов. Буферизация позволяет ускорить потоковое чтение или потоковую запись
во много раз.

Стандартная библиотека C поддерживает три режима буферизации.
* **Полная буферизация.** Обозначается константой `_IOFBF`. Данные накапливаются в буфере до его заполнения, затем записываются на устройство. При чтении сначала заполняется буфер, затем данные постепенно забираются из буфера.
* **Построчная буферизация.** Обозначается константой `_IOLBF`. Данные накапливаются в выходном буфере либо до тех пор, пока он не заполнится, либо в выводе появится символ `'\n'`.
* **Без буферизации**. Обозначается константой `_IONBF`. Буферизация отключена. Данные записываются на устройство немедленно. При чтении каждый раз выполняется операция чтения данных с устройства.

Например, если буферизация отключена, то вызов функции `fscanf` будет считывать из устройства по
одному символу. А функция `fprintf` будет выводить на устройство фрагментами сгенерированного текста,
но не обязательно по одному байту.

По умолчанию поток `stderr` создается без буферизации. У потока `stdout` буферизация построчная,
если поток связан с терминалом или псевдотерминалом, и полная в остальных случаях. То есть,
если вы запускаете программу, которая выводит на стандартный поток вывода, с терминала
без перенаправления ее вывода, стандартный поток будет построчно буферизован. Поэтому
если выводить перевод строки, например:

```c
    printf("%d\n");
```

число будет отображено на терминале немедленно после вывода.
Но если
стандартный поток вывода перенаправить в файл, он будет буферизован полностью.
Поэтому вывод с символом перевода строки может оказаться в выходном файле не сразу.
Учитывая то, что стандартный поток вывода может быть перенаправлен не только в файл,
но и в канал (pipe), на другой стороне которого другая программа будет ожидать ввод,
полная буферизация может привести к «тупикам» (deadlock) при взаимодействии процессов.
Это мы будем рассматривать в соответствующих разделах курса.

Говоря об «устройстве» с которым идет работа в потоках ввода-вывода, мы говорим не о каком-либо
физическом устройстве, а об абстракции, предоставляемой ядром операционной системы. В POSIX-совместимых
операционных системах работа с устройствами ведется с помощью _файловых дескрипторов_, о которых мы
будем подробно говорить в следующих частях курса. Терминал или псевдотерминал &mdash; это специальный
тип устройств в POSIX-совместимых операционных системах. Обычно программы-эмуляторы консольного окна
взаимодействуют с запускаемой программой именно с помощью псевдотерминала. На уровне
стандартной библиотеки C для проверки, связан ли файловый дескриптор с терминалом,
используется функция `isatty`.

Функция `fflush` принудительно записывает содержимое буфера на устройство:

```c
    printf("%d\n"); fflush(stdout);
```

Число будет выведено на устройство независимо от типа буферизации.
Функцию `fflush` можно использовать и для потоков ввода, но она будет
работать ожидаемым образом только для файлов произвольного доступа,
поэтому её использование не рекомендуется.

Перед началом операций ввода-вывода с открытым дескриптором потока
тип буферизации можно настроить с помощью функции `setvbuf`.

```c
int setvbuf(FILE *f, char *buf, int type, size_t size);
```

Параметр `type` позволяет задать тип буферизации. Например,

```c
    setvbuf(stdout, NULL, _IONBF, 0);
```

отключает буферизацию стандартного потока вывода.

Если `buf == NULL`, то параметр `size` указывает рекомендуемый размер буфера для потока. Например,

```c
    setvbuf(stdout, NULL, _IOFBF, 16384);
```

включает полную буферизацию и рекомендует установить размер буфера в 16KiB.

Можно передать уже существующий буфер, но управление памятью, выделенной под буфер,
возлагается на саму программу. Важно, чтобы передаваемый буфер не был локальной переменной,
которая будет уничтожена раньше, чем закроется файл. Если память под буфер выделялась динамически,
освобождаться она должна самой программой. Мы не рекомендуем использовать эту возможность
функции `setvbuf`, так как корректное использование буфера реализовать достаточно сложно, и, как правило,
это не нужно.

## Бинарные данные и способы их текстового представления

Программы, которые мы писали на предыдущих занятиях, работали со входными
данными в текстовом формате.

Данные в текстовом формате имеют следующие отличительные признаки:
* Они представлены в одной из текстовых кодировок. Текстовая кодировка &mdash; это правило преобразования последовательности байт в визуальные образы (глифы) на экране, бумаге или другом носителе.
* Они обычно имеют двухмерную структуру, их визуальное представление состоит из строк текста на носитете. Для навигации используется понятие строки текста и столбца в нем.
* Числа в текстовом формате записываются в виде последовательностей байтов, которые визуально преобразуются на носителе в цифры. Чтобы выполнять операции над числами, необходимо выполнить преобразование во внутреннее представление.

Для работы с текстовыми данными используются функции `fgets`, `fscanf` и аналогичные.

В отличие от текстовых, бинарные данные предполагают обработку на процессоре
с минимальными накладными расходами на преобразование во внутреннее представление.

Рассмотрим пример. Пусть дана последовательность 32-битных знаковых чисел.
Требуется просуммировать эти числа.

Если входные данные представлены в текстовом формате, мы можем открыть входной файл
в текстовом редакторе и увидим что-то подобное такому:

```
1 23383 2 -12311333
```

Человек видит, что в файле записано четыре числа, и понимает, какие значения записаны.
Но, чтобы обработать этот файл в программе, его нужно считывать последовательно,
байт за байтом, выполняя преобразования десятичных цифр в число во внутреннем
представлении. Только по размеру файла невозможно определить, сколько
цифр в нём записано, и невозможно перейти на число с требуемым
порядковым номером, не просмотрев весь файл до этого числа.

Код, который суммирует последовательность чисел из файла, выглядит примерно
следующим образом:

```c
    int x;
    long long s = 0;
    while (fscanf(f, "%d", &x) == 1) {
        s += x;
    }
```

Здесь `f` &mdash; дескриптор потока, из которого выполняется чтение.

Если входные данные представлены в бинарном формате, открыв бинарный файл
в текстовом редакторе, например vim, можно увидеть примерно такое:

```
^A^@^@^@W[^@^@^B^@^@^@Û$Dÿ
```

При некотором навыке, конечно, можно понять, какие данные хранятся в этом файле,
но это явно не предназначено для чтения человеком.

Посмотреть содержимое бинарного файла в человеко-читаемом виде можно
с помощью команды `hexdump -C`. Получим примерно такой вывод:

```
00000000  01 00 00 00 57 5b 00 00  02 00 00 00 db 24 44 ff  |....W[.......$D.|
00000010
```

Первый столбец вывода &mdash; смещение от начала файла в шестнадцатеричном виде.
Поскольку в одной строке выводится 16 байтов, смещение в каждой строке
увеличивается на 16 (или 0x10). Следующие 16 столбцов &mdash;
это значения 16 байтов файла, записанные в шестнадцатеричном виде. Один
восьмибитный байт требует две шестнадцатеричных цифры для записи.
В последнем столбце выведено представление байт в кодировке ASCII.
Байты 0-31, 127 и 128-255 заменяются на точки.

Если мы сопоставим целые числа в текстовом представлении и их же в бинарном виде,
мы заметим, что каждое число занимает 4 байта, и числа представляются как показано ниже.

| Текстовая запись | Байты в файле |
| - | - |
| `1` | `01 00 00 00` |
| `23383` | `57 5b 00 00` |
| `2` | `02 00 00 00` |
| `-12311333` | `db 24 44 ff` |

Это, забегая вперед, представление 32-битных знаковых целых чисел в дополнительном коде
в формате Little-Endian (LE). Более подробно разные варианты представлений чисел
будут рассматриваться далее в курсе. Важно то, что на большинстве современных процессоров
Intel, ARM или RiscV числа в памяти компьютера хранятся точно так же, то есть
содержимое этого файла можно скопировать в оперативную память как есть,
без обработки.

Фрагмент программы, который обрабатывает бинарный файл, может быть примерно таким:

```c
    struct stat sb;
    fstat(fileno(f), &sb);                       // запрашиваем информацию о файле
    int *data = malloc(sb.st_size);              // выделяем область памяти нужного размера
    fread(data, sizeof(data[0]), sb.st_size, f); // считываем весь файл в память одной операцией
    long long s = 0;
    for (int i = 0; i < sb.st_size; ++i) {
        s += data[i];
    }
    free(data);
```

В курсе будут рассмотрены эффективные средства работы с файлами, которые вообще
позволяют избежать копирования данных. Это файлы, _отображаемые в память_ (memory-mapped files).

И текстовые, и бинарные форматы широко используются для обмена данными. Там, где
человеко-читаемость является важным фактором, используются текстовые форматы, например
XML, JSON. Там, где эффективность обработки важнее, предпочитают бинарные форматы.

### Работа с бинарными файлами

Бинарные данные редко считываются со стандартного потока ввода или
выводятся на стандартный поток вывода, хотя в POSIX-системах с этим
нет никаких проблем. Обычно файлы в бинарном формате размещаются на файловой
системе, и работают с ними по их пути в файловой системе.
Файлы, размещенные в файловой системе, еще их называют
регулярные файлы, являются файлами произвольного доступа.
Это значит, что можно быстро переместиться на любое место открытого файла
и выполнять операции чтения или записи, начиная с этого места.

На POSIX-совместимых операционных системах бинарные файлы можно открывать точно так же,
как и текстовые с помощью функции `fopen`, передавая вторым аргументом режимы открытия 
`"r"` и другие. Однако на Windows это приведет к искажению данных при чтении или записи.
Дело в том, что в текстовых файлах Windows строки текста оканчиваются на два байта с кодами
13 и 10, что соответствует константам `'\r'` `'\n'` в программах на C. В текстовых файлах
POSIX-совместимых систем строки текста оканчиваются на один байт `'\n'`.

Когда разрабатывались
первые компиляторы языка С для операционных систем CP/M, MS-DOS и Windows в начале 1980-х годов, разработчики
решили, что для облегчения переноса программ на C, разработанных для Unix,
функции чтения из потока стандартной библиотеки C, например `getchar` будут преобразовывать пару байтов
`'\r'` `'\n'` во входном файле в один байт `'\n'`, возвращаемый программе. И наоборот,
функции записи в поток, например `putchar`, будут преобразовывать выводимый программой байт 
`'\n'` в два байта `'\r'` `'\n'` в выходном файле. Таким образом, программа на C, которая
при выполнении в Unix формирует выходной файл в формате текстовых файлов Unix, при выполнении
на Windows будет формировать текстовый файл в формате Windows. Как показала практика,
эта «фича» удобна для
простых программ, но для более сложных программ, обрабатывающих текст, либо не важна, либо вредна.

Поэтому на MS-DOS и Windows чтобы открывать файл без ненужной трансляции концов строк, в режимы открытия файла
был добавлен флаг `b`. То есть для открытия на чтение бинарных файлов вместо `"r"` нужно использовать `"rb"`,
а для записи бинарных файлов вместо `"w"` &mdash; `"wb"`. При работе на POSIX-совместимых системах можно использовать этот флаг,
но он не делает ничего. В POSIX-совместимых системах трансляция байтов концов строк не требуется.

Для побайтового чтения или записи бинарных файлов можно использовать уже знакомые нам функции
`getc`, `putc` &mdash; они работают с одним байтом. Кроме того, можно использовать функции `fread` и `fwrite`
для чтения или записи блоков данных целиком. Нужно заметить, что у этих функций неудачный набор параметров
и возвращаемое значение. Системные вызовы `read` и `write`, которые мы будем рассматривать в следующей части
курса, существенно удобнее. Пока же будем использовать функции из стандартной библиотеки C.

Чтение данных выполняется с помощью функции `fread`:

```c
size_t fread(void *ptr, size_t size, size_t n, FILE *f);
```

`ptr` должен указывать на буфер, достаточный для размещения `n` элементов массива,
каждый из которых имеет размер `size`. Функция возвращает количество элементов
массива, считанных полностью. К сожалению, такое возвращаемое значение
не позволяет отслеживать все ошибочные случаи, которые могут возникать при чтении
из потока. В POSIX-совместимых операционных системах обмен данными с устройствами
ведётся блоками байтов, а не записями какого-то фиксированного размера, поэтому
при чтении из устройства (или файлового дескриптора) системному вызову чтения
с устройства `read` передается размер буфера в байтах, то есть `n * size`.
Системны вызов `read` возвращает размер прочитанных данных в байтах.
Поэтому при использовании функции `fread` разумнее всего всегда передавать
в параметре `size` значение 1, а в параметре `n` &mdash; полный размер буфера
в памяти, то есть произведение размера элемента на количество элементов.

При чтении с помощью `fread` возможны следующие ситуации:
* Запрошенные данные были прочитаны полностью. В этом случае возвращаемое значение как раз будет равно произведению размера элемента на количество элементов.
* Запрошенные данные были прочитаны частично. Это возможно, так как если на момент вызова `fread` были готовы какие-то данные для чтения, эти данные будут возвращены немедленно, а `fread` не будет переводить программу в состояние ожидания ввода-вывода. Возвращаемое значение `fread` будет ненулевым. Частичное чтение возможно даже для регулярных файлов, находящихся на диске. 
* Был достигнут конец файла. Это означает, что данных в файле больше нет и необходимо завершить его обработку. Функция `fread` возвращает 0.
* При чтении произошла ошибка ввода, то есть устройство, с которого запрашиваются данные, по каким-то причинам не смогло их вернуть. В этом случае `fread` также возвращает 0. Чтобы отличить ситуацию конца файла от ошибки, нужно использовать функцию `feof`.

Реакция программы на частичное чтение может быть различной, в зависимости от того,
какой функционал требуется реализовать. В некоторых случаях можно передать считанную порцию
данных на обработку. В других случаях потребуется повторить операцию чтения, чтобы дочитать
недостающие данные. Иногда же можно просто проверить полноту чтения и вернуть признак ошибки,
если данные считаны не полностью.

Предположим, что определена структура `Data` и мы хотим считать последовательность записей, обрабатывая каждую запись
после чтения.

```c
struct Data {
    // определение данных
};

FILE *f = ... // здесь открываем файл f

while (1) {
    struct Data elem;
    size_t res = fread(&elem, 1, sizeof(elem), f); // выполняем чтение sizeof(elem) байтов
    if (feof(f)) {
        // достигнут конец файла
        break;
    }
    if (ferror(f)) {
        fprintf(stderr, "%s: read error: %s\n", __FUNCTION__, strerror(errno));
        fclose(f);
        return;
    }
    if (res != sizeof(elem)) {
        fprintf(stderr, "%s: short read of element\n", __FUNCTION__);
        fclose(f);
        return;
    }
    // здесь обрабатываем считанный элемент
}

fclose(f);

```

Запись данных выполняется с помощью функции `fwrite`:

```c
size_t fwrite(const void *ptr, size_t size, size_t n, FILE *f);
```

По передаваемым параметрам и возвращаемому значению эта функция похожа
на функцию `fread`. При записи не может возникать ситуации достижения
конца файла, но ошибки записи или короткие записи вполне возможны.
Обработка таких ошибок аналогична рассмотренной выше.

### Бинарные файлы произвольного доступа

Главная функция файловой системы &mdash; хранение именованных данных.
Мы говорим о файлах, у которых есть имена, которые располагаются
в каталогах и подкаталогах. Содержимое файла хранится на диске
в виде последовательности байт.
Такие файлы в терминологии POSIX-совместимых систем называются
_регулярными_ (regular file).

Файловые системы в мире POSIX-совместимых операционных систем располагаются
на так называемых _блок-ориентированных устройствах_ (block device).
Блок-ориентированное устройство с точки зрения операционной системы
представляет собой массив блоков. Обмен данными с блок-ориентированным устройством
возможен только блоками целиком, но блоки устройства доступны по своему номеру,
то есть драйвер блочного устройства поддерживает операции чтения и записи
блока с произвольным номером. Для современных SSD-дисков можно считать, что время выполнения
операции с каждым блоком не зависит от его номера.

Стандартный размер блока для блок-ориентированного устройства &mdash; 512 байт, но операционные
системы могут группировать несколько физических блоков в один логический блок, например размера 4 KiB.
В любом случае каждый блок после его загрузки в оперативную память располагается в памяти подряд.
Регулярные файлы можно представить как последовательность блоков на диске, на которых размещаются
данные этого файла. Блоки на диске не обязательно размещаются подряд, но файловая система
хранит информацию о размещении каждого блока файла на диске. Таким образом,
для каждого смещения в файле операционная система может быстро вычислить блок в файловой системе
и смещение в блоке, где размещаются данные. Регулярный файл можно представить как массив байтов,
размещенный на устройстве. Операции чтения и записи с регулярными файлами можно проводить
с любой позиции, а не только с текущей позиции чтения/записи. Такие файлы называются
_файлами произвольного доступа_. Но классический интерфейс чтения и записи с файлами
предполагает, что сначала текущая позиция в файле переносится на желаемую позицию,
затем выполняется операция ввода-вывода, при этом текущая позиция в файле сдвигается
на число байт, над которыми произведена операция.

Обратите внимание, что запись в файл с некоторой позиции **не означает** вставку данных
с этой позиции файла. Старые данные в файле будут перезаписываться новыми данными.

### Позиционирование в файле произвольного доступа

Текущую позицию в файле можно получить с помощью функции `ftello`:

```c
off_t ftello(FILE *stream);
```

Тип `off_t` &mdash; это тип для хранений размеров и смещений в файлах. Он знаковый, и
в случае смещений может быть и отрицательным. Функция `ftello` возвращает неотрицательное
значение &mdash; текущую позицию в файле &mdash; при успешном завершении.
При ошибке возвращается -1, а в переменной `errno` находится код ошибки.
Функция применима только к дескрипторам потоков, которые связаны с файлами произвольного доступа
или с блочными устройствами. К другим потокам, например к терминалу, эту функцию применить нельзя.

Для изменения текущей позиции в файле можно использовать функцию `fseeko`:

```c
int fseeko(FILE *stream, off_t offset, int whence);
```

Функция возвращает 0 при успешном завершении и -1 при ошибке. Параметр `whence` задает, относительно
какой точки отсчитывается смещение `offset`:

* `SEEK_SET` &mdash; параметр `offset` отсчитывает смещение относительно начала файла;
* `SEEK_CUR` &mdash; смещение относительно текущей позиции;
* `SEEK_END` &mdash; относительно конца файла.

Новая позиция в файле получается сложением точки отсчёта и смещения. В любом случае новая позиция не может быть
отрицательной, то есть переместится в позицию до начала файла невозможно. Если файл открыт в режиме «только чтение»,
то новая позиция не может быть больше размера файла. Если файл открыт для модификации, записи или добавления,
новая позиция может быть больше размера файла. Размер файла от этого не изменится. Но если в файл будет выполнена
запись, то данные будут записаны по новой позиции, а между старым концом файла и точкой записи будут записаны нулевые байты.

Следующий фрагмент программы позволяет определить размер файла произвольного доступа:

```c
    off_t current_pos = ftello(f);    // запомнили текущую позицию в файле f
    fseeko(f, 0, SEEK_END);           // переместились в конец файла
    off_t file_length = ftello(f);    // получили размер файла
    fseeko(f, current_pos, SEEK_SET); // вернулись на старую позицию
```

Следует заметить, что существуют более эффективные способы сделать это, используя системный вызов `fstat`,
который будет рассматриваться позже на курсе.

### Открытие файла на модификацию

Выше мы рассмотрели режимы открытия файлов `"r"` или `"w"` для чтения из файла или записи в файл.
Но для работы с файлом произвольного доступа может возникнуть потребность и считывать содержимое
из файла, и модифицировать его. Для этого файл нужно открывать в одном из следующих режимов доступа:

* `"r+"` или `"r+b"` &mdash; открытие для чтения и записи. Файл должен существовать. Текущая позиция в файле устанавливается на начало файла.
* `"w+"` или `"w+b"` &mdash; открытие для чтения и записи. Если файл не существовал, он создается, а если существовал, то очищается. Текущая позиция в файле устанавливается на начало файла.

Пример ниже добавляет в конец бинарного файла очередное число Фибоначчи. Ошибки не проверяются, добавление необходимых проверок на ошибки мы оставляем в качестве упражнения.

```c
int main(int argc, char *argv[]) {
    FILE *f = fopen(argv[1], "r+");  // открываем файл в режиме чтение/запись
    if (!f && errno == ENOENT) {
        // файл не существовал, создаем его
        f = fopen(argv[1], "w+");
    }
    fseeko(f, 0, SEEK_END);
    off_t file_length = ftello(f);   // получили размер файла
    uint64_t val = 0;
    if (file_length == sizeof(val)) {
        // в файле есть одно значение
        val = 1;
    } else if (file_length >= 2 * sizeof(val)) {
        // в файле есть как минимум два значения
        fseeko(f, -2 * (ssize_t) sizeof(val), SEEK_END);
        uint64_t olds[2];
        fread(olds, 1, sizeof(olds), f);
        val = olds[0] + olds[1];
    }
    fwrite(&val, 1, sizeof(val), f); // записываем очередное значение
    fclose(f);
}
```

## Управление выводом на терминал

Под терминалом мы понимаем физическое устройство или программу, отображающую
окно на экране компьютера, которые поддерживают операции ввода данных с клавиатуры
и отображения глифов на экране. Для отображения обычно используют моноширинные шрифты,
поэтому экран терминала представляет собой матрицу, в каждой ячейке которой можно
отобразить один глиф.

Глиф &mdash; это конкретное графическое представление буквы, цифры или другого знака.
Мы будем избегать использования слова «символ», так как и в русском, и в английском
языках оно имеет слишком много значений.

Классический размер терминала &mdash; 24 строки и 80 столбцов. До сих пор окно
программы-эмулятора терминала имеет такой размер по умолчанию, хотя, конечно, вы можете его
изменить. Самые первые терминалы были, по-сути, печатающими машинками, которые передавали
информацию о нажатых кнопках на компьютер, а данные, получаемые от компьютера,
печатали на бумаге. С тех пор сохранилось, что байт с кодом 13 (CR &mdash; Carriage Return)
вызывает перемещение печатающей головки &mdash; каретки, carriage &mdash; к левому краю листа.
Байт с кодом 10 (LF &mdash; Line Feed) вызывает промотку листа бумаги на одну строку вниз.
В совокупности пара байтов 13, 10 вызывает перемещение печатающей головки, а в современных
терминах _курсора_ в начало следующей строки. Так эти два байта, обозначающие конец строки
в текстовом файле, появились в самых первых текстовых документах, оттуда перешли в
операционную систему CP/M, оттуда в MS-DOS и далее в Windows.

С 60-х годов прошлого века существовали так называемые алфавитно-цифровые терминалы,
которые состояли из клавиатуры, которая уже стала компьютерной клавиатурой, приобретя
много дополнительных кнопок, и экрана, способного отображать цифры, буквы и различные
знаки. Алфавитно-цифровой терминал подключался к компьютеру по
_последовательному интерфейсу_, например RS-232, и передавал данные
со скоростью 9600 бод (то есть бит в секунду). К одному компьютеру могли подключаться
десятки алфавитно-цифровых терминалов, за которыми работали пользователи.
Первые терминалы были семибитные, то есть они принимали и передавали данные порциями
по 8 бит, но старший бит (бит чётности) использовался для контроля корректности передачи,
поэтому оставалось 7 значащих бит. Поэтому кодировка ASCII определяет только первые 128 байт.
Повсеместный переход на 8 значащих бит в текстовых файлах закончился лишь в 90-х годах прошлого века.

Поскольку клавиатура терминалов предоставляет больше возможностей для ввода, чем обычные буквы, цифры
и знаки, дополнительные кнопки и комбинации кнопок должны как-то кодироваться для передачи в
компьютер. Например, клавиша Del кодировалась байтом 127. Комбинация Ctrl-C кодировалась
байтом 3, комбинация Ctrl-D &mdash; байтом 4 и так далее. Но кодировка ASCII содержит только 33 места
для управляющих байтов (коды 0-31 и 127). И наоборот, возможности терминалов по выводу тоже росли,
и управляющих байтов становилось недостаточно для передачи всех возможностей терминала.

В 1975 году фирма DEC выпустила терминал VT-52, в котором для передачи кодов нажатых
клавиш на компьютер и для управления отображением информации на экране использовались
последовательности байт, начинающиеся с кода 27 (ESC). После VT-52 появился очень
популярный в своё время терминал VT-100, который развил эту систему команд,
и примерно в то же время появился стандарт "ANSI escape sequence", который стандартизовал
систему команд. Далее появлялись новые модели терминалов, например VT-320, система команд
расширялась, но в основе осталась такой же. Потом появилась программа xterm &mdash;
эмулятор терминала для X Window System, которая еще расширила набор поддерживаемых
команд, и далее все последующие эмуляторы терминалов для POSIX-совместимых операционных систем
поддерживают систему команд xterm. Консоль Windows в современных версиях Windows
также поддерживает управляющие последовательности ANSI.

Команды, управляющие выводом на экран, начинаются с байтов 27 91, которые в строке C
записываются как `"\x1b["`. Эти два стартовых байта называются CSI &mdash; Control
Sequence Introducer.

Более полное описание доступно (найдите в поиске).
Некоторые управляющие последовательности перечислены ниже:

| Последовательность | Имя | Описание |
| - | - | - |
| `CSI `_n_` ; `_m_` H` | Cursor Position | Переместить курсор в строку n, столбец m. Координаты отсчитываются от 1. |
| `CSI `_n_` J` | Erase in Display | Очистить часть или весь экран: если n == 0, очистить от курсора до конца экрана; если n == 1, очистить от начала экрана до курсора; если n == 2, очистить весь экран; если n == 3, очистить весь экран и буфер скролла |
| `CSI `_n_` K` | Erase in Line | Очистить часть и всю строку: если n == 0, очистить от курсора и до конца строки; если n == 1, очистить от начала строки до курсора; если n == 2, очистить всю строку |
| `CSI `_n_` m` | Select Graphic Rendition | Установить графические атрибуты: цвет шрифта, цвет фона |

Некоторые графические атрибуты перечислены ниже:

| Значение атрибута | Описание |
| - | - |
| 30-37 | Установить цвет шрифта: [Black, Red, Green, Yellow, Blue, Magenta, Cyan, White] |
| 38 | Установить расширенный цвет шрифта |
| 39 | Вернуть цвет шрифта по умолчанию |
| 40-47 | Установить цвет фона: [Black, Red, Green, Yellow, Blue, Magenta, Cyan, White] |
| 48 | Установить расширенный цвет фона |
| 49 | Вернуть цвет фона по умолчанию |

Специальные клавиши, например управление курсором, клавиши F1...F10, при нажатии тоже генерируют
последовательности, которые начинаются с байта 27. Но обработка нажатых клавиш в реальном времени
требует переключения терминала в _неканонический режим_, и это мы обсудим позже, в соответствующей
части курса.

Существуют библиотеки для языка C, такие как [ncurses](https://invisible-island.net/ncurses/)
и некоторые другие, которые берут на себя низкоуровневые детали работы с терминалом
и предоставляют программисту переносимый и более удобный интерфейс.

## Однобайтные и многобайтные кодировки символов

Кодировка текста &mdash; это правила преобразования последовательности байт в последовательность глифов
на графическом носителе. За время развития компьютерной техники было придумано много разных кодировок текста,
а в настоящее время доминирует кодировка UTF-8.

Кодировки могут быть фиксированного размера, в которых под каждый отображаемый глиф отводится фиксированное
количество байт, и переменного размера, в которых количество байт, кодирующих глифы, может меняться.
К кодировкам фиксированного размера относятся ASCII, CP1251; к кодировкам переменного размера &mdash; UTF-8,
UTF-16, UTF-32.

Базовая кодировка фиксированного размера &mdash; ASCII. В кодировке ASCII под глиф отводится один байт.
При этом байты со значениями 0-31 и 127 используются для управления выводом текста. Байты 128-255
не используются. В кодировке ASCII записываются исходные коды программ, за исключением символьных
и строковых констант, на большинстве языков программирования. В языке C символьная константа,
например `'0'` имеет значение ASCII-кода глифа '0' &mdash; 48. На базе ASCII существует много
однобайтных кодировок, у которых младшая половина, то есть байты со значениями 0-127 совпадают
с кодировкой ASCII, а старшая половина добавляет национальные глифы. Например, для кириллического письма
существует кодировка CP1251, которая использовалась на Windows и Mac, кодировка CP866, которая использовалась
в MS-DOS, и кодировка KOI8-R, которая использовалась на разных версиях Unix и в Интернете.

Кодировка UCS-16 &mdash; это другой пример кодировки фиксированного размера. Эта кодировка изначально использовалась
в Windows и в языке Java. Кодировка UCS-16 позволяет кодировать первые 65536 кодовых позиций (code points) Unicode.
В современной Java и Windows используется очень похожая кодировка UTF-16, в которой поддерживаются
суррогатные пары и комбинирующие кодовые позиции (combining characters aka diacritics), поэтому UTF-16 уже нельзя считать кодировкой фиксированного размера.
Если, возможно, когда-то у кодировки UCS-16 было преимущество, что глифы кодировались фиксированным числом байт,
то у современной UTF-16 такого свойства уже нет, а компактности представления обычного текста она уступает кодировке UTF-8.
Поэтому идет постепенный процесс перехода на UTF-8 в качестве единственной кодировки для текста.

В кодировке UCS-32 каждый глиф кодируется четырьмя байтами. Все примерно 160 000 кодовых позиций Unicode
кодируются четырьмя байтами каждый. Но, во-первых, для большинства глифов, которые используются повседневно,
два байта всегда нулевые, и, во-вторых, существуют комбинирующие кодовые позиции (combining characters), которые меняют визуальное представление (глиф)
последующей кодовой позиции. Поэтому кодировка UCS-32 вообще не имеет никаких плюсов. Она не является кодировкой фиксированного
размера, не совместима с ASCII и очень неэкономична для представления обычных текстов. В стандартной библиотеке C есть
набор функций для работы с _широкими символами_ (wide characters) и _широкими строками_ (wide strings), в которых
как раз используется кодировка UCS-32, но эти функции никогда не использовались широко.

## Кодировка UTF-8

Стандарт Unicode поддерживает все существующие на данный момент системы письма. Текст Unicode может кодироваться
разными способами: UTF-8, UTF-16, UTF-32, хотя самая распространенная из них &mdash; UTF-8. Некоторые современные
языки программирования, такие как Go или Rust фиксируют, что тип данных «строка» (string) хранит корректно
закодированную в UTF-8 строку Unicode. Однако полная поддержка стандарта Unicode очень сложна, и
в стандартной библиотеке реализована только базовая функциональность. Для языков C и C++
существует библиотека [ICU](https://unicode-org.github.io/icu/userguide/icu/), в которой реализована
полная поддержка стандарта.

Кодировка UTF-8 &mdash; это кодировка переменного размера. Одна кодовая позиция Unicode может кодироваться
разным количеством байт: от одного до четырех. С учетом того, что некоторые кодовые позиции сами по себе
являются комбинирующими и изменяют глиф последующих кодовых позиций, максимальная длина кодирования одного глифа
неограничена. Стандарт Unicode не накладывает ограничения на количество комбинирующих кодовых позиций,
предшествующих основной кодовой позиции.

Кодовые позиции Unicode обозначаются префиксом `U+`, за которым записывается номер позиции
в шестнадцатеричном виде. Стандарт определяет кодовые позиции от `U+0` до `U+10FFFF`, из них
диапазон `U+D800` ... `U+DFFF` запрещен к использованию (для совместимости с UTF-16 surrogate pairs).

Кодировка UTF-8 имеет следующие преимущества:
* она совместима с кодировкой ASCII, то есть для текста, который использует только кодовые позиции `U+0` ... `U+7F`, его представление в кодировках ASCII и UTF-8 идентичны;
* нулевой байт в UTF-8 соответствует единственной кодовой позиции `U+0`, его по-прежнему можно использовать как байт-терминатор строки, поэтому все функции языка C, работающие с NUL-терминированными строками, будут корректно обрабатывать UTF-8 строки;
* она самосинхронизирующаяся, то есть по любому байту в тексте в кодировке UTF-8 можно легко найти первый байт, кодирующий данную кодовую позицию.

| Число байт | Значащие биты | Первая кодовая позиция | Последняя кодовая позиция | Байт 0 | Байт 1 | Байт 2 | Байт 3 |
| - | - | - | - | - | - | - | - |
| 1 | 7  | `U+0`     | `U+7F`     | `0xxxxxxx` | | | |
| 2 | 11 | `U+80`    | `U+07FF`   | `110xxxxx` | `10xxxxxx` | | |
| 3 | 16 | `U+800`   | `U+FFFF`   | `1110xxxx` | `10xxxxxx` | `10xxxxxx` | |
| 4 | 21 | `U+10000` | `U+10FFFF` | `11110xxx` | `10xxxxxx` | `10xxxxxx` | `10xxxxxx` |

Биты кодируются по принципу Little-Endian, то есть младшие биты попадают в байты с меньшими смещениями.

Кодовые позиции Unicode должны кодироваться минимальным числом байт, то есть, например, кодирование глифа `'/'` (`U+2F`) должно занимать один байт,
а не два, три или четыре.

Одним байтом в UTF-8 кодируются глифы ASCII. Двух байт достаточно для представления всех национальных глифов европейских языков, включая кириллицу.
Три байта используются для кодирования восточных языков, например китайских иероглифов. И, наконец, четыре байта используются для кодирования эмоджи. 

Комбинирующие кодовые позиции очень сильно усложняют обработку текста в Unicode. Например, глиф `ё` имеет индивидуальную кодовую позицию `U+451`.
Но также глиф `ё` может быть получен с помощью комбинирующей кодовой позиции `U+308` и кодовой позиции `U+435`. В первом случае глиф кодируется
двумя байтами в UTF-8, а во втором случае &mdash; 4 байтами.
